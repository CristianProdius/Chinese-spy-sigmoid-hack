# Deep research: tiny, fast, accurate chapter retrieval

Output of the multi-agent research run made before implementation (five research angles, a synthesised
plan, and an adversarial critique of that plan). Several recommendations were later tested and rejected;
`../EXPERIMENTS.md` records what was actually measured.

## Plan

### Recommended architecture

Repo note: /mnt/data/projects/Chinese-spy-sigmoid-hack holds only README.md (one commit). limits.json, requirements.txt, the grader script, the public sample and corpus_meta.jsonl still have to be fetched, so every branch below is conditional on them.

CORE IDEA: all model quality goes in at build time. Query time does one shared normalization, scores several vectors over the SAME window table, takes the max over each doc's windows (MaxP), fuses the results and returns the top 3. Minimum system I expect to clear 0.80 with margin: A + B + C + one semantic leg (D1 or D2) + E1 fusion. Lexical alone (A+B) probably lands around 0.55-0.75 on vague slips, and I trust that estimate over the 0.98 simulated number, which used exact-term queries. Upgrades in order: E2 learning-to-rank, F metadata field, G domain fine-tunes, H cross-encoder.

A. Shared normalizer (stdlib only). It lives in main.py, and the build script imports it from there so build and query tokenization can never drift.
- Steps: NFKD and strip combining marks, lowercase, regex [a-z0-9]+, join digit groups, drop about 180 stopwords on both sides.
- Query-only slip-template stoplist: part, where, bit, section, chapter, passage, describe(d), mention, account, someone, something, remember, about. Learn the final list from public plus synthetic slips, and keep content cues such as 'traveller'.
- Stemmer: snowballstemmer if requirements.txt lists it, otherwise a vendored Porter/Porter2 in main.py. Wrap it in functools.lru_cache.
- Variant table index/variants.tsv (surface -> canonical), applied before stemming: Habana/Havannah -> havana, segar -> cigar, UK -> US spellings, Vueltabajo -> vuelta abajo, and Humboldt OCR variants -> clean form.
- Years: each 4-digit year from 1400 to 2029 emits its own token plus a decade token (dec1890). The query parser maps '1890s', 'eighteen-nineties' and 'mid-1890s' to dec1890. Canonicalization happens inside the token stream, so no query-time synonym-group scoring is needed.

B. Lexical passage index (numpy only).
- Windows: about 200 raw words each (stopwords counted), stride 100 (50% overlap), contiguous per doc. Every doc gets at least one window, because np.maximum.reduceat silently returns a neighbour's value for an empty segment.
- Scoring is BM25S-style: BM25 is computed at build time and stored. df and IDF are counted per window (N about 45k), so topical words like sugar, tobacco and Havana stay discriminative.
- Storage: impacts quantized to uint8 with one global scale. Term-major CSR: indptr uint32, window ids uint16 (uint32 if there are more than 65,535 windows), impacts uint8.
- A second CSR at doc level: 1552 columns, doc-level IDF, high k1/b (start at 2.5/0.8).
- Query: concatenate the postings of the query's term ids, np.bincount(minlength=n_windows), then np.maximum.reduceat(doc_start) gives MaxP. The doc-level BM25 uses the same bincount on the doc CSR.
- Lexical score = a*P/max(P) + (1-a)*D/max(D), with a about 0.7. The doc term offsets MaxP's bias toward long chapters.
- Query-time df cap: skip terms found in more than 25% of windows. This is for latency only; do no static pruning.
- Cost: about 12-16 MB raw (4-6 MB zlib). Measured p95 is about 0.3 ms.

C. LLM slip expansion (numpy at query time).
- Generation: for every window, Qwen2.5-7B-Instruct-AWQ (fits the free 8 GB) writes 5-8 slip-style recollections plus about 10 keywords. Few-shot examples are public slips, rotated. The prompt asks for one passage-specific detail in plain modern words and no titles.
- Filter (doc2query-- style): a build-time cross-encoder (bge-reranker-v2-m3) scores each (slip, window) pair, and we keep about the top 60%.
- Two ways to use the slips; ship whichever survives ablation, or both.
  - C1 expansion field: a second CSR over the same window ids. Window score = BM25(text) + w_x*BM25(exp), taken before MaxP.
  - C2 slip index: each slip is a tiny doc (uint32 ids) with a slip->doc map. Doc score = max over that doc's slips, via np.maximum.at on a 1552 array.
- Cost: +5-10 MB each, +0.5-1 ms. The LLM also writes clean vocabulary for the Humboldt OCR windows.

D. Semantic leg, chosen by requirements.txt and limits.
- D1: onnxruntime present, p95 limit of about 25 ms or more, size limit of about 45 MB or more. Asymmetric dense.
  - Build: embed the title-prefixed windows with Snowflake arctic-embed-m-v1.5 (about 1 GB of GPU, minutes). MRL-truncate to 256 dims, store int8 with a fixed +/-0.3 range, and cast once to C-contiguous fp32 at load.
  - Query encoder: MongoDB/mdbr-leaf-ir int8 ONNX (23 MB, distilled into arctic's space). Apply its 384->768 Dense layer in numpy, truncate to 256 dims, renormalize, and add the query prefix. Session options intra_op=1 and inter_op=1, plus a warm-up call in __init__.
  - Tokenizer: `tokenizers` if listed, otherwise the vendored pure-Python WordPiece. A researcher measured 0 mismatches on 1,251 lines.
  - Scoring: P @ q, then MaxP. If the p95 limit is under about 40 ms, score only the passages of the lexical top-100 docs; recall@100 must be at least 0.98.
  - Validate leaf-ir at 256 dims on V, since the model card only reports 768. Use 512 dims if 256 loses more than 1 point.
- D2: numpy only, or a p95 limit of about 15 ms or less. Inference-free learned sparse.
  - Build: run opensearch-neural-sparse-encoding-doc-v3-distill (or -gte, both Apache-2.0) over each window, optionally with its C slips appended. Keep the top 128 terms with uint8 impacts in the same CSR code as B.
  - Query: vendored WordPiece plus the shipped 30522-float IDF table, with template words zeroed.
  - Cost: about 10-17 MB, about 2 ms.
- D3: size limit of about 25 MB or less. D2 pruned to the top 64 terms per window and zlib'd. No ONNX model.
- No onnxruntime but a p95 limit of about 150 ms or more: run D1 with leaf-ir as a pure-numpy BERT forward. Store int8 weights and dequantize at load; measured 48-70 ms for 6 layers.
- Size limit of about 80 MB or more, and both legs add points on V: ship D1 and D2.

E. Fusion (numpy only).
- E1: convex combination of per-query-normalized doc score vectors, using theoretical min-max (0 for BM25 and impacts, -1 or the build-time global minimum for cosine). Weights sit on a simplex tuned on synthetic slips. Weighted RRF is only a sanity baseline: Bruch et al. found CC beat RRF on 9 of 9 datasets.
- E2 (upgrade): a listwise-softmax linear model over the top 50 CC candidates, with about 12 features:
  - the lexical signals: lexical MaxP, doc BM25 and the 2nd-best window
  - expansion field, slip index, semantic MaxP and the mean of the top-3 semantic windows
  - metadata-field score, IDF-mass coverage of the best window, number/decade matches and a candidate-local IDF score (terms shared by all near-duplicate candidates drop to about 0)
  - log n_windows, kind one-hot, and log P(kind|query) from a tiny logistic over query terms
  The weights are under 1 KB. Try a LightGBM LambdaMART dumped to arrays only if it clearly beats the linear model.

F. Metadata field: title, book, author, chapter heading, plus a 1-2 sentence LLM 'who/where/when' descriptor per doc (1552 calls). It is stored as a small BM25 field (and as a vector in D1) and serves 'the traveller who described...' slips.

Runtime rules (all branches):
- Set OMP/OPENBLAS/MKL_NUM_THREADS=1 at the top of main.py, before importing numpy.
- Never import scipy or sklearn at query time (0.22 s and 1.35 s of import, and not needed).
- One raw .npy per array. No pickle and no big JSON; the vocab is newline text loaded into a dict.
- gc.freeze() after load, and one warm-up search in __init__.
- Never do arithmetic in fp16 or int8 with numpy (12-15x slower); cast once at load.
- index/ holds only .npy, .txt, .tsv, .json and .onnx files.
- Tie-break deterministically by doc id.

Budget branches (target at most 50% of each limit, measured on our box):
- Size 20 MB or less: A + B + C with zlib'd postings + D3. No ONNX model and no metadata vectors.
- Size 30-60 MB: A + B + C + D1 (zlib the ONNX if needed, -25-30%), or D2. Then E1, then E2.
- Size 100 MB or more: everything, including D1 + D2 and optionally H.
- p95 10 ms or less: no ONNX encoder. Use D2; the whole system is about 3-5 ms.
- p95 20-40 ms: D1 with the lexical shortlist.
- p95 50 ms or more: D1 full scan.
- p95 100 ms or more, with onnxruntime: optionally H, a TinyBERT-L2 int8 cross-encoder fine-tuned on synthetic slips with near-duplicate negatives. It scores the best 128-token window of the top 5 docs and is used as one E2 feature, never as the final ranker. Ship it only if it adds at least 2 points on V.
- Load limit 1 s or less: raw .npy, no xz, no big zlib blobs, no scipy or sklearn. Load limit 3 s or more: zlib anything.

Which parts need which libraries:
- numpy plus stdlib only: A, B, C, D2, D3, E, F, the numpy-BERT fallback.
- onnxruntime: D1's leaf-ir encoder and H.
- tokenizers: always optional, since the vendored WordPiece covers D1, D2 and H.
- snowballstemmer: optional, since a vendored Porter covers A.

### Ranked techniques

- **Passage-window BM25 (about 200 words, stride 100) with MaxP plus doc-level BM25 interpolation, scored at build time into a uint8 CSR; window-level IDF**
  - *expected gain:* Foundation. Measured elsewhere: MS MARCO-doc +17% RR over default doc BM25; Callan +20-24% on long docs; a simulated buried-detail test gave 0.98 vs 0.84. Estimate +5-15 Hit@3 points over doc BM25 here.
  - *cost:* numpy only. About 12-16 MB raw (4-6 MB zlib), p95 about 0.3 ms, load about 0.1 s
  - *priority:* 1
- **Shared normalizer: accent folding, stemming (package or vendored), build-time variant/OCR canonicalization, decade tokens, slip-template stoplist**
  - *expected gain:* +2-6 points (BEIR stemming +1.3 nDCG; keyword-izing natural-language queries +6-19% for Dai & Callan). Decade and variant tokens decide some near-duplicate slips.
  - *cost:* stdlib only. Under 1 MB, under 0.5 ms
  - *priority:* 2
- **Leakage-safe synthetic slip sets (V from a different generator, T kept out of the index) plus the grader-like harness**
  - *expected gain:* No direct gain. Cuts tuning SE from about 4-6 points (public sample) to about 0.6-1 point, and is required for E2 and calibration
  - *cost:* Build time only: about 1-2 GPU-hours
  - *priority:* 3
- **Per-window LLM slip expansion with doc2query-- filtering: expansion field C1 and/or separate slip index C2**
  - *expected gain:* +5-15 points (estimate). MS MARCO-doc per-passage expansion MAP 0.269 -> 0.318 over MaxP; NQ320k full articles Hits@1 29 -> 39
  - *cost:* numpy only. +5-10 MB per variant, +0.5-1 ms. 7B AWQ on 8 GB, about 1-2 GPU-hours plus filtering
  - *priority:* 4
- **Semantic leg D1: asymmetric dense (arctic-m-v1.5 passages at 256-d int8, mdbr-leaf-ir int8 ONNX query encoder), MaxP**
  - *expected gain:* +3-10 points fused (leaf-ir asymmetric 54.0 BEIR vs BM25 41.1). Domain shift to 19th-century prose is unmeasured
  - *cost:* Needs onnxruntime (tokenizers optional). 23 MB model + about 12 MB vectors; about 15-20 ms p95 full scan, about 9 ms with the lexical shortlist; load about 0.5 s
  - *priority:* 5
- **Semantic leg D2: inference-free learned sparse (OpenSearch doc-v3-distill/gte), uint8 impacts in the same CSR**
  - *expected gain:* +3-8 points fused (BEIR 50.4 vs BM25 44.5, biggest gains on Wikipedia sets: NQ 32.6 -> 52+). Overlaps partly with C
  - *cost:* numpy only (vendored WordPiece). 10-17 MB, about 2 ms
  - *priority:* 6
- **Convex-combination fusion with theoretical-min-max normalization (E1)**
  - *expected gain:* Required to realize the hybrid gain; 1.5-3 points over RRF (Bruch, 9 of 9 datasets)
  - *cost:* numpy only. Negligible size, under 0.5 ms
  - *priority:* 7
- **Listwise linear learning-to-rank over about 12 features, including near-duplicate features (candidate-local IDF, coverage, number/decade match, kind prior) (E2)**
  - *expected gain:* +2-6 points (estimate; Coordinate Ascent +7.8% on description queries; oracle-alpha headroom 0.04-0.10)
  - *cost:* numpy only. Under 10 KB, 1-3 ms
  - *priority:* 8
- **Humboldt OCR cleanup (dehyphenation, SymSpell to the clean vocabulary, variant map) plus a per-source bias**
  - *expected gain:* +0.5-2 points overall, +10-30% relative on that slice (Parapar et al.)
  - *cost:* Build time only; under 0.5 MB
  - *priority:* 9
- **Metadata/LLM descriptor field per doc (F)**
  - *expected gain:* +1-3 points, mostly 'the traveller who...' slips
  - *cost:* numpy only. Under 1 MB; 1552 LLM calls
  - *priority:* 10
- **Domain fine-tunes (G): query encoder aligned to frozen passage vectors, or doc-v3 sparse fine-tuned with same-topic hard negatives**
  - *expected gain:* +3-8 points (low confidence), concentrated on near-duplicates
  - *cost:* GPU-hours at build; no runtime change
  - *priority:* 11
- **Fine-tuned TinyBERT-L2 int8 cross-encoder on the best window of the top 5 docs, as one E2 feature (H)**
  - *expected gain:* 0 to +4 points, unproven. Off-the-shelf TinyBERT scores BELOW BM25 on BEIR (42.2 vs 43.4)
  - *cost:* onnxruntime. 4.5 MB, about 15-25 ms (VNNI-dependent)
  - *priority:* 12
- **Bigram/phrase postings (SDM-style)**
  - *expected gain:* 0-3 points, mostly on multiword names
  - *cost:* numpy only. +5 MB, +0.2 ms
  - *priority:* 13
- **SKIP: PRF/RM3, off-the-shelf static embeddings (potion, static-retrieval-mrl), static index pruning, rank_bm25, HNSW/faiss, scipy/sklearn at query time, SumP, whole-chapter vectors, uniCOIL/EPIC, linear DSI-style scorer**
  - *expected gain:* Flat or negative for Hit@3, or dominated by the options above (PRF: DL21 MRR -5%; SumP 0.38 vs MaxP 0.98; pruning beyond 10% of postings costs 1-11 points)
  - *cost:* n/a
  - *priority:* 14

### Build steps

- 1. Fetch and read the task files: limits.json, requirements.txt, the grader script, the public sample and corpus_meta.jsonl. Compute total words, per-kind length distribution, the window count at 200/100 (does it fit uint16?), the public sample size n and its answer kind mix. Measure: n, which gives Hit@3 SE = sqrt(0.16/n), and pick the D and budget branches from the recommended architecture.
- 2. Build the harness before any model. (a) An evaluator for Hit@3 and MRR@10 with a per-kind breakdown and a confuser report: for each miss, is the top-1 a same-topic doc from another source? (b) A grader-like runner: fresh subprocess, taskset -c 0, thread env vars set to 1, corpus directory absent. It times `import main` and Retriever(index_dir) separately, then runs 1000 search() calls and reports p50/p95/max with and without the first call. It also runs du -sb on main.py + index/ and checks that index/ holds no code or pickle. Baseline: doc-level BM25 with normalizer A. Record the numbers.
- 3. Generate the tuning sets before tuning anything. V (validation): 2-3k slips from a generator or prompt different from the expansions. Use Qwen 32B/72B when the GPU frees, otherwise the 7B with a distinct persona and temperature, plus optionally a few hundred slips written by Claude subagents for a different model family. Sample windows uniformly by depth within each chapter and stratify kinds to match the public mix. Have an LLM judge relabel each slip against the top-10 candidates and drop ambiguous ones. T (training): 5-10k slips from a separate generation run, never put in the index. Measure: Kendall tau between V and the public sample over 5+ early variants (doc BM25 default and tuned, MaxP at 3 window sizes). Require tau >= 0.6, otherwise rework the V prompt.
- 4. Passage BM25 with MaxP plus doc-level interpolation (component B). Grid: window {150, 200, 300} with stride half the window; passage k1 0.9-2.0 and b 0.3-0.75; doc k1 1.2-4 and b 0.6-0.9; a 0.5-0.9; MaxP vs best + 0.5*second. Keep it if V Hit@3 beats doc BM25 by at least 3 points and the public sample is not worse. Confirm that uint8 impacts give the same Hit@3 as fp32.
- 5. Normalizer extras (component A): accent folding, variant table, decade tokens, template stoplist, Humboldt OCR cleanup (dehyphenation, running heads, SymSpell correction against the clean vocabulary) and a per-source bias. Ablate each on V. Judge the OCR cleanup on V's Humboldt slice. Keep each one only if V does not drop; the OCR cleanup must lift the Humboldt slice.
- 6. If the D1 branch is possible, embed all windows with arctic-embed-m-v1.5 now (minutes, about 1 GB of GPU), before the long generation job takes the 8 GB.
- 7. LLM slip expansion (component C). Generate for all windows with Qwen2.5-7B-Instruct-AWQ under vLLM, with prefix caching and gpu_memory_utilization set to fit the FREE memory. Apply the cross-encoder filter, then ablate C1 vs C2 vs both, the w_x grid and the keep-% grid. Measure V Hit@3 twice: with expansions for all windows (matches test conditions) and with the expansions of V's source windows removed (pessimistic bound). Keep it if both improve by at least 2 points and the public sample is not worse. Record added size and p95.
- 8. Semantic leg (D1, D2 or D3, by branch). Measure standalone Hit@3 on V and the public sample, the fused gain under E1, and the p95 and size it adds. For D1, also measure leaf-ir at 256 vs 512 dims and the shortlist's recall@100. Keep it if the fused V gain is at least 2 points and total p95 stays at or under 50% of the limit.
- 9. Fusion. E1: tune CC weights on T with 5-fold CV grouped by doc, then confirm on V and the public sample. E2: train the listwise linear model on T. Keep E2 only if it gains at least 1.5 points on V with paired bootstrap p < 0.1 and the public sample is not worse. Inspect the weights: the kind prior must not dominate (955 of 1552 docs are Wikipedia).
- 10. Near-duplicate features (candidate-local IDF, number/decade match, coverage) and the metadata/descriptor field F, each ablated inside E2. Keep the features with a positive fold-averaged gain.
- 11. Only if V is below 0.85 or the public sample is below 0.88: domain fine-tune (G). Either align the query encoder to the frozen arctic passage vectors, or fine-tune the doc-v3 sparse encoder, on slips with same-topic hard negatives from other docs. Then try H if latency allows. Measure V, the public sample and p95.
- 12. Freeze. Rebuild from scratch with one script and run the grader-like runner in a clean directory without the corpus, on a quiet core. Confirm size, load and p95 at 50% of the limits or less, public Hit@3 >= 0.88, V >= 0.85, and identical output across reruns.

### Biggest risks

- Style shift between synthetic and hidden slips: a config that wins on LLM slips can lose on the hidden set. Mitigate with a different generator for V, several prompt styles, a tau >= 0.6 proxy check and the public sample as a veto.
- Overfitting the small public sample (SE about 4-6 points at n = 50-100). Never tune more than 2-3 scalars on it, and aim for 0.88 public to clear 0.80 hidden.
- Near-duplicate confusions ('many books tell the same history'). Semantic legs and topic-level expansions make same-topic chapters look more alike. Counter with specific-detail expansion prompts, rare-term, number and candidate-local IDF features, and the confuser report.
- Build/query tokenization mismatch (stemmer, variant map, WordPiece) silently zeroing matches. Keep one normalizer in main.py imported by the build, and parity-test the vendored WordPiece against tokenizers.
- Dependency surprise: if onnxruntime is absent, D1 dies. The numpy-only path (B + C + D2 + E) must reach the target on its own, or fall back to the numpy BERT forward when latency allows.
- Latency on the unknown 'old machine': int8 ONNX loses about 2x without AVX512-VNNI, and our measurements came from a heavily loaded shared Xeon. Keep p95 at 50% of the limit or less, and use the lexical shortlist for dense scoring when tight.
- Silent array bugs: uint16 window-id overflow above 65,535 windows; np.maximum.reduceat returning a neighbour's value for docs with zero windows; fp16/int8 numpy arithmetic being 10-15x slower if not cast at load.
- Leakage that inflates validation: T or V slips appended to the index, or learning-to-rank trained on the same generation used for the expansion field.
- Limited GPU (8 GB free): expansions and slips come from a 7B model, which writes noisier and more hallucination-prone slips. The cross-encoder filter and LLM relabeling matter more as a result.
- Load-time blowups from scipy or sklearn imports, big JSON vocab dicts, xz-compressed models or fp32 casting of large matrices when the load cap is about 1 s.
- Humboldt OCR slice and long PG chapters under-ranked against short, clean Wikipedia articles (955 of 1552 docs). Watch the per-kind Hit@3 and the kind-prior weight in E2.

### Evaluation protocol

Three question sets with fixed roles.
- T: 5-10k LLM slips, a separate generation run that is never put in the index. Used to fit learning-to-rank, calibration and fusion weights, with 5-fold CV grouped by source doc.
- V: 2-3k slips from a different generator or prompt (and ideally a different model family) than both the expansions and T. Windows are sampled uniformly by chapter depth, kinds are stratified to the public sample's answer mix, and an LLM judge relabels each slip against the top-10 candidates; ambiguous slips are dropped and tracked separately. V is used for every architecture and parameter decision.
- Public sample: validation only. Tune at most 2-3 scalars on it, and only with repeated 5-fold CV.

Rules:
- Index conditions: score V under realistic conditions (expansions exist for every window, as at test time) and under a pessimistic condition (expansions removed for V's source windows). Accept a change only if both improve.
- Proxy check: before trusting V, rank 5-10 early pipeline variants on V and on the public sample and require Kendall tau >= 0.6.
- Comparing variants: use a paired bootstrap or McNemar test on discordant questions, never raw means. At n = 50-100 the public Hit@3 SE is about 4-6 points, so public differences of 3 points or less are noise. A change ships only if V improves by at least 1.5-2 points (paired p < 0.1) and the public sample does not get worse.
- Reporting: always report Hit@3 and MRR@10 per source kind (Wikipedia, PG travel, PG history/report, Country Study, Humboldt OCR) and the confuser rate (top-1 is a same-topic doc from another source).
- Leakage: never evaluate on slips that are in the index. Keep T, V and expansion generations disjoint and seeded.
- Ship gate: public Hit@3 >= 0.88 and V >= 0.85. The grader-like runner (fresh process, taskset -c 0, thread env vars set to 1, corpus absent, clean directory) must show size, load and p95 at 50% of the limits or less, with p95 measured on a quiet core and reported with and without the first call.

## Critique of the plan

### Verdict

The plan gets the mechanics mostly right. The CSR + bincount + reduceat lexical design is fast, storing int8 and casting to fp32 at load is right, and the leaf-ir/arctic pairing checks out: 22.6M params, 6 layers at 384 hidden, a 384->768 Dense layer, a 23 MB int8 ONNX, and BEIR 53.55 standard / 54.03 asymmetric, aligned to arctic-embed-m-v1.5. Its accuracy claims are borrowed priors and its validation design will overstate the gains. The biggest problem: V, T and the expansions can all come from the same Qwen 7B, rotated public slips go into the expansion prompts, and ambiguous slips are dropped from V. Together these make the doc2query and fusion legs look better than they will on hidden slips, and the 0.85/0.88 gates mean less than they appear to. It is also too complex for a hackathon with an unknown deadline. Simplest path I expect to clear 0.80: window BM25 MaxP plus doc BM25, plus a full-scan dense leg (D1 if onnxruntime is listed, otherwise a trained static query encoder into arctic space), plus CC fusion with 2-3 tuned scalars and LLM-cleaned Humboldt text. Add C, E2 and the rest only if public is under 0.88, measured on a different-family V. Fix the measurement setup first: this box is at load average 582, so latency there needs CPU-time measurement and an old-machine factor. Use reduceat, not np.maximum.at (about 10x faster on my run), skip the lexical shortlist for dense, and work on a separate branch because the repo root already holds another challenge's main.py.

### Flaws

- **Validation sets V and T, plus the C expansions, can all come from Qwen2.5-7B ('otherwise the 7B with a distinct persona and temperature'), and fusion/E2 weights are fitted on T.**
  - *problem:* If the same model writes the expansions and the evaluation slips, the expansions match those slips in wording, so the C1/C2 features look far stronger on T and V than they will on the hidden slips. E2 and CC then over-weight the expansion legs, and the V gate measures model self-agreement instead of retrieval. The plan treats a 'separate run' or 'distinct persona' as independent, but they are not. This is the classic doc2query evaluation bias.
  - *fix:* Make V come from a different model family. Claude subagents on the subscription are available now; don't wait for the 72B/32B to free up. Prefer a different family for T as well, or at least a different prompt template and few-shot pool. Report the C gain as V(other family) minus V(no C) and trust only that number. If T has to come from the 7B, fit only 2-3 fusion scalars on V and drop E2.
  - *severity:* high
- **The minimum system is A+B+C+D+E1, with E2, F, G and H as upgrades, three synthetic sets, LLM-judge relabeling, a Kendall-tau proxy check and paired bootstrap gates.**
  - *problem:* This is a research program, not a hackathon plan. The first scored submission depends on fetching the files, generating V/T, judge relabeling and a multi-hour 7B generation job on a GPU that has only 8 GB free. The deadline is unknown, so the real risk is shipping nothing that passes. It also goes against the instruction to build as simply as possible.
  - *fix:* Gate by stage and keep a shippable submission at every stage. Hour 1: A-lite + B (window BM25 MaxP plus doc BM25), measured on public and in the grader-like runner. Day 1: add D1 (arctic passages plus leaf-ir query) or D2, with E1 tuned on 2-3 scalars. Run C, E2, F, G and H only if V or public is below target, in that order, and stop as soon as public is >= 0.88 with headroom on every limit.
  - *severity:* high
- **An LLM judge relabels each V slip against the top-10 candidates; ambiguous slips are dropped and tracked separately, and the ship gate is V >= 0.85.**
  - *problem:* The hidden set still contains its ambiguous near-duplicate slips, each with one gold doc. Dropping them from V removes exactly the cases the task calls the main difficulty, so V overstates hidden Hit@3. Relabeling against our own top-10 also biases the labels toward the current system.
  - *fix:* Compute the gate on the full V with the original single gold. Use the judge only to tag slips as multi-gold for diagnostics, never to remove them from the gate. Report Hit@3 separately on the ambiguous slice.
  - *severity:* medium
- **C uses rotated public slips as few-shot examples, and the public sample is the veto and ship gate (public >= 0.88).**
  - *problem:* When a public slip's gold window is processed with that slip in the prompt, the 7B can copy its wording into the expansion. The public questions then match their own expansions almost exactly, which inflates the public veto, the one signal that is not synthetic.
  - *fix:* Use K-fold few-shot: never show a window's prompt a public slip whose gold doc is that window's doc. Better, use paraphrased or Claude-written style exemplars, and keep the public slips out of every generation prompt.
  - *severity:* medium
- **Latency and import costs were measured on our box (p95 about 0.3 ms lexical, numpy BERT 48-70 ms, sklearn import 1.35 s), and step 12 measures 'on a quiet core'.**
  - *problem:* s10926048 had a load average of 582 on 48 cores while I checked. My microbenchmark there showed a 45k x 256 fp32 matvec at about 8 ms p50, which is roughly 2-3x what a quiet core should do. Wall-clock p95 on this box is mostly noise from other tenants, and there is no quiet core to measure on. The org policy also asks agents to keep load on this box small.
  - *fix:* Measure time.thread_time() or perf stat instruction counts per search() to get CPU-time p95. Run the grader-like runner on the big CPU box or the Mac with an isolated core. Apply an explicit old-machine factor (2-3x) before comparing against limits.json.
  - *severity:* medium
- **For D1 under a p95 limit below about 40 ms, score only the passages of the lexical top-100 docs (needs recall@100 >= 0.98).**
  - *problem:* The dense matvec is the cheap part: about 2-4 ms on a quiet core for 45k x 256 fp32. The ONNX encoder (about 25 tokens including the 10-token prompt, 6 layers, 1 thread) costs more and the shortlist does not save it. Fancy-indexing a row subset also copies memory. The shortlist loses recall on exactly the paraphrase slips where the lexical leg fails and dense is needed, so recall@100 >= 0.98 is unlikely on vague slips.
  - *fix:* Always scan the full dense matrix. If latency is tight, cut dims (256 to 128 with MRL) or the window count (stride 150 or 200 for the dense leg only) instead. Spend the latency budget on the query encoder.
  - *severity:* medium
- **Humboldt OCR cleanup: dehyphenation, running heads, SymSpell correction against the clean vocabulary, and a variant map; the LLM 'also writes clean vocabulary'.**
  - *problem:* SymSpell corrects single tokens within edit distance 2. Heavy or synthetic OCR noise (split and merged words, multi-character confusions) defeats it. The hidden Humboldt slips were probably written from the clean meaning, so lexical and WordPiece-dense matching both break on that slice. SymSpell is the weakest tool for the job.
  - *fix:* Have an LLM rewrite every Humboldt window into clean English at build time (about 600 windows, which is cheap even on the 7B), and index both the raw and the cleaned text under the same doc id for the lexical and dense legs. Check whether the rules allow external build-time text; the 1856 Derby & Jackson scan is on Internet Archive (archive.org/download/islandofcuba00humb) and HathiTrust. Add a char-trigram BM25 field for that slice only.
  - *severity:* medium
- **The expected gains (+5-15 doc2query, +3-10 dense, 0.98 vs 0.84 buried-detail simulation, SumP 0.38 vs MaxP 0.98) are cited as support, and SumP and soft aggregation are skipped.**
  - *problem:* These numbers come from MS MARCO and BEIR, where queries are keyword-like or specific, or from a toy simulation with exact-term queries. They say little about vague paraphrased slips over 19th-century prose. Using the toy result to skip soft aggregation is weak evidence: slips that summarize a section can favor top-k mean or log-sum-exp over the windows. The doc-v3-distill card reports a BEIR average of 0.517 and gives no BM25 baseline, so the '50.4 vs 44.5' comparison does not come from it.
  - *fix:* Treat every gain as an unmeasured prior. Add soft-MaxP (top-2 mean over non-overlapping windows, LSE with temperature) to the step-4 grid. Rank components by the measured V and public deltas from step 2 onward.
  - *severity:* low
- **C2 doc score = max over that doc's slips via np.maximum.at on a 1552 array.**
  - *problem:* ufunc.at is slow. With numpy 2.5 on 300k slips I measured np.maximum.at at 1.9 ms p50 and 2.6 ms p95, against 0.19 ms for np.maximum.reduceat over doc-sorted slips. numpy before 1.25 is several times slower again, and the grader's numpy version is unknown. Separately, slip ids need uint32, so C2 postings are about 5 bytes each; the 5-10 MB estimate holds only after zlib.
  - *fix:* Sort slips by doc and use np.maximum.reduceat with doc_start, applying the same empty-segment guard as B. Budget C2 at about 15 MB raw.
  - *severity:* low
- **Generate 5-8 slips plus about 10 keywords for every window (about 45k with 50% overlap) on the 7B AWQ within the free 8 GB, in about 1-2 GPU-hours.**
  - *problem:* Overlapping windows double the generation cost and add no coverage. AWQ weights take about 5.6 GB, which leaves roughly 1-1.5 GB of KV cache (about 56 KB per token for Qwen2.5-7B), or about 25-30 concurrent 900-token sequences. On an H100 another tenant is already loading, 15M+ output tokens is more likely 2-5 hours. If that tenant grows, the job dies mid-run. The 7B is also not in the cache (only 32B and 72B AWQ are listed).
  - *fix:* Generate on non-overlapping 200-word windows and map each slip to both overlapping windows that contain it. Use an fp8 KV cache, shard the job into resumable chunks that write JSONL, and download the 7B up front.
  - *severity:* low
- **Proxy check: Kendall tau >= 0.6 between V and the public sample over 5+ early variants.**
  - *problem:* With 5 variants there are 10 pairs, so tau = 0.6 means 2 discordant pairs, which is not significant (p about 0.12). Public-sample noise of 4-6 points also reorders variants that differ by only a few points. The check passes or fails mostly by chance.
  - *fix:* Compare 10+ variants that are deliberately spread out (doc BM25, MaxP, dense alone, fused). Check that V and public agree on the sign of each large delta (5+ points), not on rank correlation.
  - *severity:* low
- **Query-time df cap: skip terms found in more than 25% of windows (for latency only), and the 'best + 0.5*second' window variant.**
  - *problem:* Lexical p95 is already about 0.3-0.5 ms, so the cap saves nothing, but it does change rankings for mid-frequency topical terms. With 50% overlap, the second-best window is usually the best window's neighbour, so the variant mostly double-counts one passage.
  - *fix:* Drop the df cap unless profiling shows a need. Define 'second' as the best window that does not overlap the top one.
  - *severity:* low
- **E2's kind prior is log P(kind|query) from a logistic fitted on T, where T is stratified to the public mix.**
  - *problem:* The prior learns whatever kind mix T was sampled with. Errors in that mix, or a hidden mix that differs, carry straight into ranking, with 955 of 1552 docs being Wikipedia.
  - *fix:* Fit the logistic on class-balanced T and add log(public kind frequency) as a separate scalar bias that is tuned (or shrunk to uniform) on the public sample.
  - *severity:* low
- **The repo holds only README.md (one commit); use the leaf-ir int8 ONNX as-is.**
  - *problem:* The repo now holds a different challenge (Braided River) with main.py at the root, so a new main.py would overwrite it. The leaf-ir int8 ONNX ships as two files, model_quantized.onnx (220 KB) plus model_quantized.onnx_data (23 MB). An .onnx_data file may fail an index/ format whitelist. Leaf-ir's mean pooling includes the prompt and special tokens (include_prompt: true) before the 384->768 Dense layer, which is easy to replicate wrong without noticing.
  - *fix:* Work on a separate branch or worktree, or in a subdirectory. Re-save the ONNX as a single file (onnx.save with external data off; under 2 GB is fine). Parity-test the numpy pooling, Dense layer and normalize path against sentence-transformers output to 1e-3 cosine on 1k slips.
  - *severity:* low

### Missing ideas

- A trained static query encoder in arctic's space: an IDF-weighted bag-of-words embedding table, initialized by Model2Vec-distilling leaf-ir or arctic, then fine-tuned contrastively on slip->window pairs against the frozen arctic window vectors with same-topic hard negatives. It needs only numpy at query time, runs in under 1 ms, takes about 10-13 MB at int8 for the corpus vocab, needs no onnxruntime, and is trained on slip style. It is a much better numpy-only path than a numpy BERT forward.
- A learned term-translation table (IBM Model 1 or a translation LM in the Berger and Lafferty style) fitted on synthetic slip->source-window pairs. It expands each query term into its top-k corpus terms with weights ('rolled leaves' -> tabaco/cigar, 'Spaniards first saw' -> Columbus/1492). It is numpy-only, a few MB, and is the lexical counterpart of the dense leg for vague paraphrases.
- Fold the generated slips into the dense leg at no size cost: window_vec = normalize(arctic(window) + lambda * mean(arctic(slips of that window))). Tune lambda on V before building a separate C2 index.
- A specificity filter for expansions instead of plain doc2query-- relevance: keep a slip only if the cross-encoder scores it higher on its own window than on the best same-topic window from another doc. The task's core difficulty is near-duplicates, and a plain relevance filter keeps topic-generic slips while it can drop the vague-but-specific ones.
- Literal near-duplicate detection at build time with MinHash over windows. Wikipedia Cuba articles often include Library of Congress Country Study text verbatim (it is public domain). Duplicated passages should leave both docs eligible for the top 3, with a source prior learned from public as the tie-break.
- Query-side fuzzy matching for 'from memory' misspellings of Spanish names (Cienfuegos, Cespedes, Vuelta Abajo, Pinar del Rio): map each OOV query token to its nearest corpus vocab term through a small char-trigram -> term index, applied after accent folding.
- Multi-granularity windows: a second, coarser window size (about 600 words) for MaxP, or as an E1 leg, for slips that describe a whole section or table (sugar statistics that span pages) and not one 200-word passage.
- Choose the top 3 by calibrated P(gold) rather than raw score order. When a near-duplicate cluster spans sources, a per-kind calibrated probability decides whether to spend the third slot on another source.
- Use Claude subagents on the subscription as the primary V generator (a different model family, available now), mimicking the organizer process: sample a deep passage and write a vague no-title slip. Don't let V wait for the 32B or 72B to free up.
- Wikipedia section headings and PG chapter headings as a heading-path prefix for each window (title > section > subsection) in both the lexical text and the dense text, not just the doc title.
- Check whether build-time external data is allowed (rules). If it is, a cleaner Humboldt text (Internet Archive or HathiTrust OCR of the 1856 edition) aligned to the noisy chapters is the biggest single fix for that slice.
- A per-query timing breakdown in the harness (normalize, lexical, encoder, dense, fusion) using thread_time, so cuts go to the real bottleneck (likely the ONNX encoder, not the scans).

## Research by angle

### lexical

**Top recommendation:** Build the block-decomposed passage BM25 first. Store one block-level inverted index of 100-word blocks (uint16 ids + uint8 tf, about 10 MB). At query time, form 200- and 300-word overlapping windows by shifted sums, take MaxP per doc, and interpolate with a doc-level BM25 computed from the same postings. Use block-level IDF and the normalization pipeline: Snowball stemming, accent folding, spelling-variant and decade synonym groups, and slip-template stopword removal. Why this first: it targets the two stated difficulties head-on (long docs with buried passages, natural-language slips). It runs on numpy alone in an estimated 2-5 ms with near-instant load. The evidence is strong: Callan reports +20.7-23.5% on long Federal Register docs, Kaszkiel & Zobel +18-37%, and MS MARCO-doc +16.7% RR over default doc BM25. It also makes the system much less sensitive to length-normalization tuning, which matters with a small public tuning set. Do the cheap build-time OCR cleanup of the Humboldt slice (dehyphenation, SymSpell correction, variant groups) in the same pass. Tune everything on LLM-generated synthetic slips plus the public sample to avoid overfitting. Second step: per-passage LLM expansion (doc2query-- style, Qwen2.5-7B-AWQ fits the free 8 GB), the largest purely lexical lever against paraphrase mismatch (+18% MAP over MaxP on MS MARCO-doc). Then fuse with the dense leg from the other researchers through the small coordinate-ascent combiner. Skip PRF for final ranking: it lifts recall but leaves top-rank metrics flat or down (DL21 MRR -5%). Treat proximity bigrams as optional. My unverified expectation: lexical alone probably lands around 0.55-0.75 Hit@3 on vague slips, so 0.80 likely needs expansion plus hybrid fusion.

#### Techniques

- **Block-decomposed passage BM25: MaxP plus doc-score interpolation (the core lexical leg)**
  - *how it works:* Tokenize each doc (pipeline from the normalization technique), then cut it into consecutive NON-overlapping blocks of B=100 tokens, counting stopwords so a block is about 100 words of text. Store one block-level inverted index: per term, the arrays blk (uint16 if under 65,536 blocks, else uint32) and tf (uint8). Add blk_doc (doc id per block), doc_first_blk, blk_len and block-level df. At query time, scatter the postings of the q query terms into a dense float32 matrix T[n_blocks, q]. Overlapping windows come from shifted sums: W200 = T[:-1]+T[1:] (200 words, stride 100) and W300 = T[:-2]+T[1:-1]+T[2:]. Mask any window whose first and last blocks belong to different docs. Apply BM25 saturation per window with block-level IDF and window lengths, then sum over query terms. Per-doc passage score = np.maximum.reduceat(window_scores, doc_first_window). Alternatives: log-sum-exp with temperature tau (tau->0 gives MaxP, large tau approaches SumP) or best+0.5*second-best. Doc-level BM25 = np.add.reduceat(T, doc_first_blk) with doc lengths and its own k1/b. Final score = alpha*P/max(P) + (1-alpha)*D/max(D), normalized per query so alpha is stable. Callan used D+7W on Federal Register and D+2W on West, so tune alpha in 0.5-0.9. Overlapping windows cost no storage because they are summed at query time. Any window size that is a multiple of B is available.
  - *expected effect:* Primary lexical evidence: Callan SIGIR'94 (INQUERY window passages). Federal Register (long, heterogeneous docs): 11-pt AP 30.8 doc-only -> 37.2 best-passage (+20.7%) -> 38.0 with D+7W (+23.5%). West legal (very long docs, strong 55.1 baseline): +3.8% MaxP, +5.5% D+2W. Passage-size sweep from 25 to 1000 words: 150-300 is best, and 200-250 is the safest single choice. Kaszkiel & Zobel 1997 (arbitrary fixed-length passages): +8% on TREC disks 2&4, +18-37% on Federal Register. MS MARCO-doc dev (Anserini, 10-sentence windows, stride 5): default BM25 RR@100 is 0.2299 full-doc vs 0.2684 MaxP (+16.7%). Tuned full-doc (k1=3.44, b=0.87) 0.2778 vs tuned MaxP 0.2756 is a tie, so passages mostly remove the need for fragile length-normalization tuning. DL19 nDCG@10 0.5176 -> 0.5302. Dai & Callan 2019 (150-word windows, stride 75, Robust04 nDCG@20 title/desc): FirstP 0.444/0.491, MaxP 0.469/0.529, SumP 0.467/0.524, so FirstP is worst when evidence is buried. Sheetrit et al. 2019 doc+max-passage interpolation (300-term windows) gives small gains on news/web (WT10G MAP .195->.209, Robust .254->.254). My estimate for these chapter-length docs with buried passages (not measured): +5-20% relative Hit@3 over untuned doc BM25, +0-8% over a well-tuned doc BM25, with the biggest effect on long book chapters.
  - *index size cost:* Assuming a corpus of about 4-5M words (unverified): about 45k blocks of 100 words, about 55 unique content stems per block, about 2.5M postings. At 3 bytes per posting (uint16 block id + uint8 tf) that is about 7-8 MB. Block->doc map, lengths and df add under 0.5 MB, vocab (100-150k terms) 1-2 MB. Total about 10 MB. Doc-level BM25 is derived from the same postings at no extra cost.
  - *query latency cost:* Estimated, not measured: 2-5 ms per query on one thread with numpy for 8-12 query terms. That covers scattering 20-60k postings into an approx. 2 MB dense matrix, 2 shifted adds, saturation, row sums and reduceat. Python tokenization/stemming adds under 0.5 ms. If the limit is about 10 ms on an old CPU, drop terms with very low IDF, or score windows only for the top-200 docs by doc-level BM25.
  - *query time dependencies:* numpy only (np.load, fancy indexing, reduceat, argpartition). No scipy needed.
  - *build recipe:* Pure Python/numpy on the CPU box, minutes. Grid search on the public sample plus 300-1000 synthetic slip-style questions generated by an LLM from random held-out passages (Qwen2.5-7B-Instruct-AWQ fits in the free 8 GB; 32B/72B once the GPU frees). Grid: window in {150,200,300} (B=50 or 100), passage k1 in [0.9,2.2] and b in [0.3,0.75], doc k1 in [1.2,4.5] and b in [0.6,0.9], alpha in [0.5,0.9], aggregator in {max, LSE tau, top-2}. Cross-validate. Save .npy uncompressed (fast load) unless the size limit forces savez_compressed.
  - *risks:* MaxP favors long docs: more windows give a higher expected max (extreme-value effect). Keep the doc-level term or subtract c*log(n_windows). Windows must not cross doc boundaries (mask). With fixed-length windows, b barely matters except for short Wikipedia stubs that form one partial window. Interpolation needs per-query score normalization. Many knobs tuned on a small public set will overfit, so tune on synthetic slips.
  - *sources:* ['https://maroo.cs.umass.edu/pub/web/getpdf.php?id=105', 'https://dblp.org/rec/journals/jasis/KaszkielZ01.html', 'https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/msmarco-v1-doc-segmented.md', 'https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/msmarco-v1-doc.md', 'https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/dl19-doc-segmented.md', 'https://arxiv.org/pdf/1905.09217', 'https://arxiv.org/pdf/1906.02083']
  - *confidence:* high
- **BM25 parameterization for heterogeneous long docs: high k1/b at doc level, BM25+/BM25L lower bound, block-level IDF**
  - *how it works:* Doc level, where lengths range from short Wikipedia articles to 10k-word chapters: Lucene BM25 idf=log(1+(N-df+0.5)/(df+0.5)), tf part tf*(k1+1)/(tf+k1*(1-b+b*dl/avgdl)). For long docs, search high k1 (2-4.5) and high b (0.75-0.9). BM25+ adds delta=1.0 to the saturated tf for every matched term. BM25L uses c=tf/(1-b+b*dl/avgdl), then (k1+1)(c+delta)/(k1+c+delta) with delta=0.5. Both put a floor under the length penalty so very long chapters are not over-penalized. Passage level (fixed 200-300-word windows): k1 0.9-2.2, b nearly irrelevant. IDF: compute df over BLOCKS (N about 45k), not docs (N=1552). Across 1552 long chapters, topical words (sugar, tobacco, slaves, Havana, insurrection) appear in a large share of docs and their doc-level IDF collapses toward 0. Block-level IDF keeps them discriminative. Query term frequency: count repeated query words once or cap them.
  - *expected effect:* Variant choice matters little. Kamphuis et al. ECIR 2020 found no significant differences among 8 BM25 variants. BM25S on BEIR (avg nDCG@10 at k1=1.2, b=0.75): Robertson, ATIRE, BM25+ and Lucene all 39.9, BM25L 39.5. Parameters matter more: Lucene at k1=0.9, b=0.4 gets 41.1. Long docs want high k1 and b: MS MARCO-doc full-doc RR@100 0.2299 at (0.9,0.4) -> 0.2778 at (3.44,0.87) (+21%). On segmented passages tuning only moves 0.2684 -> 0.2756 (+2.7%). Lv & Zhai CIKM 2011 report that lower-bounding (BM25+/BM25L) helps over-penalized long docs, especially for verbose queries; I could not retrieve their exact numbers. Estimate for this task: doc-level tuning +5-15% relative; BM25+/L vs BM25 +/-1-2 points; block-level IDF is a reasoned guess (no direct citation), likely positive for topical words.
  - *index size cost:* None beyond the passage index; block-level df is already stored (about 0.5 MB as int32 for 100-150k terms).
  - *query latency cost:* None (same arithmetic).
  - *query time dependencies:* numpy only.
  - *build recipe:* Grid search on public plus synthetic slips (see the passage technique). Seconds per configuration with numpy, since all scoring is vectorized.
  - *risks:* Overfitting k1/b to a small public set. High doc-level b penalizes long chapters relative to short Wikipedia articles, which interacts with the passage weight alpha, so tune them jointly. BM25L/BM25+ give every matched term a floor, so they reward long docs containing many query terms once each. That can favor broad survey chapters over the specific one.
  - *sources:* ['https://cs.uwaterloo.ca/~jimmylin/publications/978-3-030-45442-5_4.pdf', 'https://arxiv.org/html/2407.03618v1', 'https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/msmarco-v1-doc.md', 'https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/msmarco-v1-doc-segmented.md', 'https://doi.org/10.1145/2063576.2063584']
  - *confidence:* high
- **Corpus-aware normalization: Snowball stemming, accent folding, spelling-variant and decade synonym groups, slip-template stopwords**
  - *how it works:* Doc and query side share identical code: NFKD plus stripping combining marks (Guines/Güines, Marti/Martí, Rio/Río), lowercase, regex [a-z0-9]+, join digit groups (1,234,567 -> 1234567), and drop a stopword list of about 180 words (SMART/Lucene) on the doc side. Then the Snowball English stemmer. Build-time variant groups go in a JSON term->group table. They cover UK/US spellings (labour/labor, harbour, traveller/traveler, colour) and historical or Spanish spellings found in the corpus (Havana/Habana/Havannah, segar/cigar, Vuelta Abajo/Vueltabajo). Variant candidates are vocab pairs with edit distance <=2 and high context cosine from a build-time word2vec, hand-checked for the top 200. Query side: also drop slip-template words (part, where, bit, section, chapter, passage, describe/described, mention, talk, about, remember, someone, something, account, article). Learn that list from words frequent across public and synthetic slips that do not discriminate. Do not drop content cues like 'traveller'. Expand years: '1890s' / 'eighteen-nineties' -> group {1890..1899}, 'mid-1850s' -> {1853..1857}. Score each group Lucene SynonymQuery-style: per-window tf = sum of member tfs, df = df of the union (precomputed for static groups, computed from the postings union for decades). That way a 10-year expansion counts as ONE query concept instead of ten. Optional: top-3 neighbors per query term from corpus-trained word2vec at weight 0.2, stored as a small table.
  - *expected effect:* Stemming: BM25S Table 2 on BEIR, avg nDCG@10 38.4 -> 39.7 with Snowball (+1.3, +3.4% rel; Quora +5.6, DBPedia +2.9, TREC-COVID +2.8). A stopword list alone adds +0.1 for keyword queries. Natural-language queries need keyword-ization: Dai & Callan Robust04 (SDM nDCG@20) description 0.404 vs its keyword version 0.427 (+5.7%), narrative 0.278 vs keywords 0.332 (+19%). Global corpus-trained embedding expansion (Diaz et al. ACL 2016, NDCG@10): trec12 0.514 -> 0.545, robust 0.467 -> 0.475, web 0.216 -> 0.234 (+2-8%). Year and variant groups have no published number; they only fire on some slips, but there they are often the only thing separating near-duplicate histories. Combined estimate: +2-6 points Hit@3.
  - *index size cost:* Variant/decade group table under 0.5 MB. Optional embedding-neighbor table 1-3 MB. No stem map is needed if stemming runs at query time.
  - *query latency cost:* Under 0.5 ms. Pure-python Snowball is about 14x slower than PyStemmer per its PyPI page, roughly tens of microseconds per word, fine for about 15 words. Group tf merging is one extra add per group.
  - *query time dependencies:* numpy; stemmer via `snowballstemmer` (pure Python, 104 KB wheel) if it is in requirements.txt. Otherwise vendor a ~200-line Porter/Snowball implementation into main.py (code is allowed there, not in index/), or ship a precomputed surface->stem dict for corpus vocab plus an English wordlist, with a light suffix-strip fallback.
  - *build recipe:* CPU, minutes. gensim word2vec/fastText on about 5M tokens takes minutes. A VarCon UK/US list plus a manual pass over the top 200 auto-detected variant pairs. Unit-test that build-time and query-time tokenization produce identical ids.
  - *risks:* Any build/query stemmer mismatch silently zeroes matches. Over-stemming merges distinct names. Template-word removal can drop a real cue. Embedding expansion drifts toward dominant corpus topics (Diaz: global embeddings are coarse), which is exactly the near-duplicate failure mode, so keep its weight low and tune it.
  - *sources:* ['https://arxiv.org/html/2407.03618v1', 'https://arxiv.org/pdf/1905.09217', 'https://arxiv.org/pdf/1605.07891', 'https://pypi.org/project/snowballstemmer/']
  - *confidence:* high
- **OCR-robust handling of the Humboldt slice: build-time correction plus character-n-gram fuzzy variant groups**
  - *how it works:* The corpus is present at build time, so fix the index side, since queries are clean. (1) Join line-end hyphens (tobac-\nco), delete running heads, page numbers and footnote markers (lines that repeat across pages), and normalize ligatures. (2) V_clean = tokens of the other ~1500 clean docs plus an English dictionary. For each Humboldt token not in V_clean, generate SymSpell candidates within Damerau-Levenshtein <=2, weighted by OCR confusion costs (rn/m, li/h, cl/d, c/e, ii/n, tli/th, 1/l, 0/o) and by clean-corpus frequency. Replace the token when one candidate clearly wins, and keep the original as a variant. (3) For the remaining OOV tokens, compute word-internal padded char 3-4-gram sets over the vocabulary. For each clean term, store its OCR variants (Dice >=0.7 and ED <=2) as members of its synonym group, so query time pays nothing extra. Optional: a slice-only word-internal 4-gram BM25 index fused with word scores. Parapar used weight 0.53 on words and the rest on 5/4/3/2-grams at about 5% CER. Optional: LLM paragraph correction (Qwen2.5-7B-AWQ fits 8 GB), accepting only token edits that land in V_clean so no content is hallucinated. Add a tuned per-source additive bias so Humboldt chapters are not systematically outscored by clean near-duplicates telling the same history.
  - *expected effect:* Parapar et al. ECIR 2009 on the TREC-5 Confusion track (known-item, 49 topics, MRR). Word-only VSM: 0.687 clean, 0.588 at about 5% CER, 0.343 at about 20% CER. Word+char-n-gram fusion: 0.769, 0.728 and 0.471 (+12%, +24%, +37%). Harding, Croft & Weir 1997: n-gram indexes beat word indexes once degradation is about 10% or more. Bazzo et al. ECIR 2020: retrieval degrades significantly from about 5% WER, and stemming improves robustness. The overall Hit@3 gain is capped by the share of hidden questions targeting Humboldt chapters (unknown). If that share is 3-5%, expect +0.5-2 points overall and +10-30% relative within the slice.
  - *index size cost:* Correction is free. Variant table under 0.5 MB. A vocab-level n-gram->term sparse matrix for fuzzy lookup of OOV query words is about 6 MB, 1.5M nonzeros (optional). A slice-only passage n-gram index is about 3-5 MB. AVOID full-corpus passage-level char n-grams (about 50-100 MB).
  - *query latency cost:* 0 ms for precomputed variant groups. About 1-3 ms for fuzzy lookup of OOV query words via the sparse n-gram matrix (bincount). About +1 ms for slice-only n-gram scoring.
  - *query time dependencies:* numpy only.
  - *build recipe:* CPU, minutes for SymSpell over a vocabulary of about 150k words. Optional LLM correction is about 1 GPU-hour for the slice. Check correction precision by eyeballing 200 random replacements.
  - *risks:* Bad corrections can merge distinct Spanish or Cuban proper nouns. Protect tokens that are frequent in clean docs, and keep originals as variants. n-gram fusion adds noise on clean text if weighted too high. Without per-source calibration, the Humboldt slice stays under-ranked even after correction.
  - *sources:* ['https://www.dc.fi.udc.es/~barreiro/publications/parapar_etal_ecir2009.pdf', 'https://bibtex.github.io/ECDL-1997-HardingCW.html', 'https://ir.webis.de/anthology/2020.ecir_conference-20202.13', 'https://trec.nist.gov/data/t5_confusion.html']
  - *confidence:* medium
- **Per-passage LLM expansion (doc2query-- style) indexed as a second weighted field**
  - *how it works:* At build time, for each 200-word window (stride 100), prompt an instruct LLM with the passage and 3-5 public slips as style examples. Ask for 3-5 short questions a reader would scribble from memory, in plain modern words, focused on the passage's SPECIFIC details (names, numbers, unusual facts) and not the general topic, plus about 10 keywords. Filter generations whose BM25 or cross-encoder score against their own passage is low (Doc2Query-- filtering) and dedupe. Tokenize with the same pipeline, then store expansion postings in a second array aligned to the same block ids. Window score = BM25F-style: merge tf_text + w_x*tf_exp before saturation (or BM25(text) + w_x*BM25(exp)). The expansions carry modern vocabulary across the 1850-1920 wording gap (cigar for segar, statistics for tables of hogsheads, enslaved people for negroes).
  - *expected effect:* MS MARCO-doc dev MAP from the docTTTTTquery README, BM25 default. Full doc 0.2310; full doc + per-doc doc2query 0.2886 (+25%); MaxP passages 0.2688 (+16%); MaxP + per-PASSAGE doc2query 0.3182 (+38% vs full doc, +18% vs MaxP); recall@1000 0.8856 -> 0.9490. Per-passage beats per-doc for long docs. Doc2Query-- (Gospodinov et al. ECIR 2023): filtering hallucinated queries gives up to +16% effectiveness and -33% index size vs unfiltered doc2query. Vocabulary mismatch is likely the dominant failure for vague paraphrase slips, so this is the biggest purely lexical lever. My estimate: +5-15 points Hit@3 over plain passage BM25 if generated slips resemble the hidden slips (uncertain).
  - *index size cost:* About 60 extra tokens per 100-word stride, +40-60% postings, about 4-6 MB at 3 bytes per posting.
  - *query latency cost:* About +0.5-1 ms (one more field over the same blocks).
  - *query time dependencies:* numpy only (expansions are just more postings).
  - *build recipe:* About 45k windows x about 120 output tokens = 5-6M generated tokens. With about 8 GB VRAM free: Qwen2.5-7B-Instruct-AWQ (~5.5 GB) under vLLM, batched, roughly 1-2 h (estimate). Qwen2.5-32B-AWQ needs about 18-20 GB of weights, so wait for the GPU; 72B-AWQ about 40 GB. CPU llama.cpp is too slow for 32B at this volume. Hold out a passage set whose expansions are NOT used when generating synthetic tuning slips.
  - *risks:* Hallucinated expansions create false matches (filter them). Topic-level expansions make near-duplicate chapters look even more alike, so the prompt must ask for specific details. Style mismatch with the hidden slips. This overlaps with the generative/semantic researchers' angle; coordinate so it is built once.
  - *sources:* ['https://github.com/castorini/docTTTTTquery', 'https://arxiv.org/abs/2301.03266', 'https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/msmarco-v1-doc-segmented.md']
  - *confidence:* medium
- **Term proximity: bigram/phrase postings (SDM-style) scored inside passage windows**
  - *how it works:* Build time: after stopword removal and stemming, record ordered adjacent content-stem pairs within sentence boundaries (optionally skip-1 pairs, like an unordered window of 3). Keep pairs with corpus frequency >=2, plus all pairs inside capitalized multi-word names. Encode each key as a*V+b in int64, store a sorted key array, and keep postings in the same block format as unigrams. Query: form adjacent pairs of query content stems and of detected names, look them up with np.searchsorted, and score them as extra BM25 'terms' in the same windows with weight lambda. SDM defaults are 0.85 unigram / 0.10 ordered / 0.05 unordered; tune lambda in 0.1-0.3. Alternative: store the token-id sequence and compute BM25TP-style minimum-distance pair scores (idf_a*idf_b/dist^2) only for the top-20 candidate windows.
  - *expected effect:* Dai & Callan table (Indri, Robust04 nDCG@20): BOW 0.417 -> SDM 0.427 title (+2.4%), 0.409 -> 0.427 description (+4.4%). ClueWeb09-B 0.268 -> 0.279 and 0.234 -> 0.235. Büttcher et al. SIGIR 2006 BM25TP: GOV2 P@10 0.529 -> 0.600 (+13%), but TREC45 0.382 -> 0.381 (0); gains grow with doc length and collection size. Huston & Croft 2014: SDM needs tuning, and some BM25 proximity variants degrade. Since 200-word windows already reward co-occurrence, I expect only +0-3% Hit@3 here. That gain is concentrated on multiword names (Vuelta Abajo, Pinar del Rio, Ten Years' War, Platt Amendment).
  - *index size cost:* +30-60% of unigram postings after df>=2 pruning (about 3-5 MB, estimate). The token-sequence alternative is about 16-20 MB at uint32 for about 4-5M tokens, or about 12 MB packed as uint24.
  - *query latency cost:* About +0.5-1 ms for bigram terms; about 1-2 ms for the token-sequence rerank of 20 windows.
  - *query time dependencies:* numpy only.
  - *build recipe:* CPU, minutes.
  - *risks:* Paraphrased slips rarely keep exact word adjacency. A lambda set too high rewards any passage with a common phrase (sugar cane, Spanish government). Adds size for small gain, so build it only if the size budget is comfortable.
  - *sources:* ['https://arxiv.org/pdf/1905.09217', 'https://ir.webis.de/anthology/2006.sigirconf_conference-2006.90', 'https://ciir-publications.cs.umass.edu/pub/web/getpdf.php?id=1115']
  - *confidence:* medium
- **Small learned combiner over lexical features (coordinate ascent), with BM25F title/source as features rather than fixed boosts**
  - *how it works:* For the top-50 docs from passage BM25, compute about 10-14 features. Per-query max-normalized doc BM25; best-window BM25 at 200 and 300 words; 2nd-best window; LSE over windows; fraction of query IDF mass covered by the best window (concept coverage, which separates the specific chapter from near-duplicates sharing only topic words); bigram score; expansion-field score; title-field BM25 (Wikipedia title, book title, chapter heading); log doc length; log n_windows; source-kind one-hot (Wikipedia / travel narrative / report-history book / Country Study / Humboldt). Add a source-kind prior from the slip text: a tiny multinomial logistic regression over query tokens ('traveller', 'figures', 'article', 'statistics' -> kind), trained on public plus synthetic slips. Add the dense-retriever score here if another researcher's leg exists. Fit with coordinate ascent maximizing Hit@3/MRR, or pairwise logistic, using cross-validation and L2. Query time is one dot product.
  - *expected effect:* Dai & Callan Robust04 nDCG@20: Coordinate Ascent over BOW 0.417 -> 0.427 (title, +2.4%) and 0.409 -> 0.441 (description, +7.8%). The gain is larger for natural-language queries like these slips. A fixed title boost is risky: Pyserini BEIR multifield (title+body) vs flat BM25 is a wash on average, e.g. TREC-COVID 0.595 -> 0.656 but Touche 0.442 -> 0.367 nDCG@10. Learn the title weight instead. Estimate +2-6 points Hit@3, mostly from calibrating the doc-vs-passage weight and the per-source bias.
  - *index size cost:* Under 10 KB of weights plus about 3 KB of per-doc source and length arrays.
  - *query latency cost:* Under 0.3 ms for 50 candidates x about 12 features.
  - *query time dependencies:* numpy only.
  - *build recipe:* Minutes on CPU. Training queries = public sample + 500-2000 LLM-generated slips from held-out passages, with a fixed seed. Report CV Hit@3 on the public set only.
  - *risks:* Overfitting a small public sample: use few features, regularize, and lean on synthetic slips. Synthetic-vs-hidden distribution shift. Leakage if the same synthetic slips were also indexed as expansions.
  - *sources:* ['https://arxiv.org/pdf/1905.09217', 'https://castorini.github.io/pyserini/2cr/beir.html', 'https://ir.webis.de/anthology/2004.cikm_conference-2004.6']
  - *confidence:* medium
- **Pseudo-relevance feedback (RM3 / Rocchio / Bo1): test, but expect no Hit@3 gain**
  - *how it works:* Run first-pass passage BM25 and take the top 3-10 windows. Estimate expansion weights with RM3 (P(w|R) proportional to the sum over windows of P(w|window)*score), Bo1 (Bose-Einstein divergence) or Rocchio (mean tf-idf). Keep 10-20 terms, mix with the original query at weight 0.5-0.8, and rerun. This needs a forward index (per-window term lists = transpose of the inverted index) or the stored token sequence. Selective variant: apply PRF only when the first-pass top score or margin is low.
  - *expected effect:* Anserini Robust04: BM25 -> +RM3 MAP 0.2531 -> 0.2908 (+15%), P@30 0.3102 -> 0.3349 (+8%). On top-heavy metrics that resemble Hit@3, PRF is flat or negative. DL19 doc nDCG@10 0.5176 -> 0.5174; DL19 segmented 0.5302 -> 0.5684 (+7%); DL20 doc 0.5286 -> 0.5254; DL20 segmented 0.5281 -> 0.5202; DL21 doc MRR@100 0.8466 -> 0.8044 (-5%), even though R@1000 rises 0.6915 -> 0.7623. With a single target doc and many near-duplicate histories, PRF pulls toward the majority topic. Expect -3 to +3 points Hit@3. It is useful only as a recall stage feeding a reranker.
  - *index size cost:* About +7 MB for a forward index (or reuse the token sequence if it is stored for proximity).
  - *query latency cost:* About 2x first pass plus term extraction: +3-6 ms.
  - *query time dependencies:* numpy only.
  - *build recipe:* No extra build beyond the forward index; tune fb_docs, fb_terms and orig weight on synthetic slips.
  - *risks:* Topic drift into near-duplicate chapters, doubled latency, unstable tuning. Low priority.
  - *sources:* ['https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/disk45.md', 'https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/dl19-doc.md', 'https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/dl20-doc-segmented.md', 'https://github.com/castorini/anserini/blob/master/docs/reproduce/from-document-collection/dl21-doc-msmarco-v2.1.md']

### learned-sparse

**Top recommendation:** Build it in this order. Everything is numpy-only at query time, the index is about 30-60 MB total, p95 latency should be about 5 ms or less on one thread, and load time is under 1 s.

(1) Passage-level BM25 baseline. Cut each chapter into 150-300-word passages, index with pure-Python Porter stemming, and take doc score = MAX over its passages. Do not index whole chapters: on MS MARCO-doc, per-passage indexing alone lifts MAP 0.231 -> 0.269.

(2) The LLM slip engine. This is the biggest lever because the hidden slips are paraphrases of one buried passage. Qwen2.5-7B-Instruct-AWQ (5.57 GB) fits the ~8 GB free now; 14B-AWQ (9.98 GB) and 32B-AWQ (19.33 GB) do not, so use 32B/72B only if the GPU frees up. Have it write 5-10 vague 'slips' per passage for EVERY passage, few-shot with the public sample slips and told to name a passage-specific detail, then filter doc2query-- style with a cross-encoder. Use the slips two ways: (a) appended to their passage, and (b) as a separate slip index, BM25 question-to-question matching aggregated per doc. Fuse (a)+(b) with weights tuned on a separately generated validation set from a different model or prompt. Evidence: full-Wikipedia-article NQ320k goes Hits@1 29->39 and Hits@10 60->70 with filtered doc2query; MS MARCO-doc per-passage expansion gives MAP 0.231->0.318.

(3) Fuse in an inference-free learned sparse model. Use OpenSearch doc-v3-gte or doc-v3-distill (Apache-2.0) run offline on passages (plus their slips), uint8-quantized impacts, MaxP aggregation. The query side is WordPiece plus a 122 KB weight lookup; my pure-Python WordPiece matched HF tokenizers on 1,251/1,251 lines at 0.19 ms/query. Published BEIR evidence: 44.5 BM25 -> 47.0 SPLADE-v3-Doc -> 50.4 Geng/OpenSearch, with the largest gains on Wikipedia sets (NQ 32.6 -> 52-53). That covers the paraphrase cases BM25 misses.

Only if Hit@3 on synthetic validation plus the public sample is still below 0.80: (4) fine-tune the doc-only sparse encoder and a learned query-token table on the synthetic slips with near-duplicate hard negatives, and/or (5) try a linear query->doc scorer trained on the slips.

Why this order: (1)-(3) are low-risk, published, and fit any plausible size/latency/load limit with room to spare. They also leave the remaining effort for the near-duplicate problem, which only in-domain synthetic training addresses.

#### Techniques

- **Per-passage LLM 'slip' expansion (doc2query / InPars / Promptagator-style) on a passage-level BM25 index with MaxP aggregation, plus doc2query-- filtering**
  - *how it works:* Offline: split each of the 1552 docs into passages of about 150-300 words (sentence-aligned, 50% stride or no overlap; the docTTTTTquery doc recipe used 10-sentence windows with stride 5). For EVERY passage, not just the first 512 tokens, prompt a local LLM with the passage, the doc title and source (as context only), and 6-8 public sample slips as few-shot style examples. Ask it to write 4-8 short 'slips': vague noun-phrase recollections in the sample style ('the part where...', 'the X figures for Y in the 1890s', 'the traveller who described...'). They must cover different facets (scene or event, statistic or table, person described by role, place description, argument or opinion). They must use everyday paraphrases instead of the passage's rare words (cigars -> 'rolled leaves'), give no book or article titles, and name a detail specific to THIS passage, since other chapters tell the same history. Then filter doc2query-- style: score each (slip, passage) pair with a cross-encoder offline (any reranker, build-time only) and keep the top 50-70%, which drops hallucinated or generic slips. Append the kept slips to their passage text. Index at the passage level with BM25 (word tokens, lowercase, Porter stem). At query time, score the passages and take doc score = max over its passages (Score-max/MaxP). Optionally add a small doc-level BM25 term. The LLM also writes clean vocabulary for the noisy Humboldt OCR passages ('tobaeco' -> 'tobacco'), which makes expansion double as OCR repair.
  - *expected effect:* Strongest evidence on long docs: on NQ320k, whose docs are FULL Wikipedia articles, BM25 Hits@1/Hits@10 = 29.27/60.15 and BM25+docT5query with 50 cross-encoder-filtered queries per doc = 39.13/69.72 (+10 / +9.6 points; DSI-QG paper). On MS MARCO-doc, MAP goes 0.2310 (whole-doc BM25) -> 0.2688 (per-passage, no expansion) -> 0.2886 (per-doc expansion) -> 0.3182 (per-passage expansion), so passage indexing and per-passage expansion add up. On MS MARCO passage, RR@10 goes 0.185 (BM25) -> 0.279 (Doc2Query n=80) -> 0.323 with ELECTRA keep-30% filtering (Doc2Query--, +16%), and the index is 33% smaller than unfiltered. Out of domain, GENERIC MS MARCO-trained docT5query adds only +1.6% avg over BM25 on BEIR (e.g. TREC-COVID 0.656->0.713, NQ 0.329->0.399, FiQA 0.236->0.291, but FEVER 0.753->0.714). Gains therefore hinge on style-matching: Promptagator few-shot vs zero-shot prompts gave +2.3 nDCG@10 avg (47.8 vs 45.5), and round-trip filtering a further +2.5. LLaMA-3.1-8B expansion (30 queries/doc) on BEIR-small with BM25: FiQA 0.247->0.288-0.297, NFCorpus 0.322->0.337-0.342. My estimate for this task, an extrapolation: +8-20 Hit@3 points over passage-BM25. This is probably the single largest lever, because the hidden slips are paraphrases of one buried passage.
  - *index size cost:* Small. The corpus is about 1552 chapter docs, roughly 4-8M words, giving about 20-30k passages. Adding 5 slips of about 15 words each to 25k passages adds about 1.9M tokens (about 25-40% more postings). A BM25 inverted index with uint16 passage ids and uint8/float16 tf-norm weights takes about 10-20 MB. A word vocab plus a stem lookup takes 1-3 MB as JSON or npz.
  - *query latency cost:* Measured on one pinned core of the dev box with numpy (synthetic Zipfian index of 25k passages, 3.6M postings, 15-token queries, bincount accumulate + np.maximum.reduceat to 1552 docs + argpartition top-3): mean 1.38 ms, p95 2.09 ms, worst case with the 15 most frequent tokens about 3.9 ms. Regex tokenization plus stemming in pure Python adds under 0.1 ms.
  - *query time dependencies:* numpy only. Tokenizer: regex lowercase split plus a pure-Python Porter stemmer inside main.py (about 150 lines, no nltk). Alternatively, ship a precomputed word->stem dict built offline, which misses unseen surface forms. Stopword list as JSON.
  - *build recipe:* (1) Chunk docs into passages and keep passage->doc offsets contiguous so reduceat works. (2) Generation: run vLLM with the shared few-shot prefix and --enable-prefix-caching. Measured HF weight sizes: Qwen2.5-7B-Instruct-AWQ 5.57 GB (fits the ~8 GB free with about 2 GB of KV), 14B-AWQ 9.98 GB (does not fit), 32B-AWQ 19.33 GB (needs the GPU freed or vLLM --cpu-offload-gb, which is slow). Set --max-model-len about 3072 and gpu_memory_utilization to fit the FREE memory, because vLLM refuses to start if the request exceeds free memory. Rough budget for 25k passages: about 25M prefill tokens (mostly cached prefix) and 3-4M decode tokens, about 0.5-1.5 h on the 7B in an 8 GB slice. Use 32B/72B if the GPU frees up, since bigger models paraphrase more faithfully and hallucinate less. Sample at temperature 0.7-0.9 with n=2 calls of 4 slips each for diversity, and dedupe near-identical slips. (3) Filter with a cross-encoder (build-time PyTorch is fine) and keep about 60%; tune the keep-% on the validation slips. (4) Tune BM25 k1/b separately for passages and doc fusion; with expanded text, b around 0.4-0.75 is typical.
  - *risks:* Hallucinated or generic slips attach to the wrong near-duplicate chapters. Filtering mitigates this, and so does prompting for passage-specific details. Appended slips are diluted by BM25 length normalization if you index whole chapters instead of passages. Over-fitting to the generator's phrasing: if the hidden slips came from a different writer, gains shrink (BEIR generic-docT5query shows this: +1.6% only). The leakage trap: never evaluate on slips that were also appended to the index.
  - *sources:* ['https://arxiv.org/pdf/2206.10128v3', 'https://github.com/castorini/docTTTTTquery', 'https://arxiv.org/html/2301.03266v3', 'https://arxiv.org/pdf/2104.08663', 'https://arxiv.org/pdf/2209.11755', 'https://arxiv.org/html/2510.09557v1', 'https://arxiv.org/abs/2301.01820', 'https://huggingface.co/api/models/Qwen/Qwen2.5-7B-Instruct-AWQ']
  - *confidence:* high
- **Separate pseudo-slip index (question-to-question matching, RePAQ/FAQ-style) fused with passage BM25 ('dual-index' instead of append)**
  - *how it works:* Store each kept synthetic slip as its own tiny document in a second BM25 index (slip -> passage id -> doc id). At query time, compute BM25 over the slip collection. The slip->doc score is the max over that doc's slips, or a sum of its top-2 or top-3 slips, which rewards docs with several matching slips. Fuse with the passage-BM25 doc score using a weighted sum of max-normalized scores or RRF (k=60), with weights tuned on synthetic validation. Matching a short vague slip against short slips avoids the length-normalization dilution that appending causes on 5-10k-word chapters. It also turns the problem into near-duplicate question matching, which lexical BM25 does well. The original text index stays clean for slips that use the book's own wording.
  - *expected effect:* No direct BM25 dual-index numbers exist; the closest evidence is dense. Doc2Query++ reports dual-index fusion beating append on every BEIR set (Contriever; no-exp / append / dual nDCG@10: SciFact 0.657/0.656/0.729, FiQA 0.332/0.322/0.369, NFCorpus 0.331/0.332/0.361). DSI-QG shows that representing docs by their generated queries (and learning on them) reaches NQ320k Hits@1 63.49 vs 39.13 for append-style BM25+docT5query. PAQ/RePAQ shows question-to-question retrieval over pre-generated questions is competitive when the generated set covers the test distribution. My estimate: +2-6 Hit@3 over append alone, and the two are complementary (keep both).
  - *index size cost:* 100-150k slips x about 10 unique content terms = 1-1.5M postings. Using uint32 slip ids + uint8 tf takes about 5-8 MB, plus a slip->doc uint16 map (about 0.3 MB). Raw slip text is not needed at query time.
  - *query latency cost:* Same machinery as the passage index (bincount over postings + np.maximum.reduceat or a scatter-max by doc), well under 2 ms on one thread at this size. Fusion of the two 1552-length vectors costs microseconds.
  - *query time dependencies:* numpy only (same tokenizer/stemmer as the passage index).
  - *build recipe:* Reuse the generated and filtered slips from technique 1. Generate MORE slips for this index (8-12 per passage), because coverage matters more than precision here. Index them with BM25 using k1 about 1.2 and lower b, since slips are short. Tune the aggregation (max vs top-2 sum) and the fusion weight on the held-out synthetic validation set, then confirm on the public sample.
  - *risks:* Generic slips that apply to many chapters ('the part about the sugar harvest') cause ties between near-duplicate docs, so the specificity instruction plus a round-trip or ambiguity filter matters more here. The index is only as good as generator coverage: if a hidden slip targets a facet the LLM never wrote about, only the text index can rescue it. Never tune on slips that are themselves in the index.
  - *sources:* ['https://arxiv.org/html/2510.09557v1', 'https://arxiv.org/pdf/2206.10128v3', 'https://arxiv.org/abs/2102.07033', 'https://arxiv.org/pdf/2209.11755']
  - *confidence:* medium
- **Inference-free learned sparse retrieval (SPLADE-doc family: OpenSearch doc-v3-gte / doc-v3-distill / doc-v2-mini, naver SPLADE-v3-Doc), passage-level with Score-max aggregation**
  - *how it works:* Offline, run a doc-only SPLADE encoder over every passage, optionally with its synthetic slips appended, as DeepImpact/uniCOIL do with docT5query. Each passage becomes a 30522-dim sparse vector of WordPiece-token impacts. That includes expansion tokens not in the text, such as 'cigar' and 'tobacco' activated for a passage about rolled leaves, or clean tokens for OCR-garbled words. Keep the top 128-256 terms per passage, quantize them linearly to uint8 (DeepImpact found 8-bit linear quantization lossless), and store a term->(passage_id uint16, weight uint8) inverted index. At query time no model runs. Tokenize with BERT-uncased WordPiece, then weight each query token by a static lookup: binary for SPLADE-v3-Doc, the shipped IDF / query_token_weights for the OpenSearch models (a 30522-float vector, 122 KB). Compute the sparse dot product with each passage and take doc = MAX over passages. Do NOT max- or sum-pool chapter segments into one doc vector: on MS MARCO-doc, Rep-sum MRR@10 drops 36.6 -> 12.2 at 5 segments, while Score-max stays at about 36.2-36.8, and on Robust04, Score-max gives 44.9 -> 46.4 as segments grow. Fuse with BM25 and the slip indexes via a weighted sum.
  - *expected effect:* BEIR-13 nDCG@10 (Geng et al. Table 3): BM25 44.48, SPLADE-v3-Doc 46.97, Geng/OpenSearch inference-free 50.35, siamese SPLADE-v3-Distil 49.99, so the inference-free model matches the query-encoder model. The OpenSearch model card self-reports avg 0.546 for doc-v3-gte (133M), 0.517 for doc-v3-distill (67M) and 0.497 for doc-v2-mini (23M). The biggest gains over BM25 come on Wikipedia-based sets, which matters because 955/1552 of our docs are Wikipedia: NQ 32.6 -> 52.1 (v3-Doc) / 53.1, DBPedia 28.7 -> 36.1 / 40.5, HotpotQA 60.2 -> 66.9 / 67.9. BM25 still wins on Touche (34.7 vs 27.0), so fuse rather than replace. MS MARCO dev MRR@10: SPLADE-v3-Doc 37.8 vs BM25 18.7. Expected here: +3-10 Hit@3 over BM25+expansion alone when fused. Paraphrase robustness is its main contribution. Applying a 512-token MS MARCO-trained encoder to 19th-century prose and OCR is a domain shift, so validate.
  - *index size cost:* 25k passages x 128-256 kept terms = 3.2-6.4M postings x 3 bytes (uint16 pid + uint8 w) = about 10-20 MB. My benchmark index of 3.6M postings was 10.75 MB. Query side: vocab.txt 231 KB + 30522-float weights 122 KB (OpenSearch query_0_SparseStaticEmbedding/model.safetensors is exactly 122,168 bytes). No model weights ship.
  - *query latency cost:* Measured: pure-Python WordPiece median 0.19 ms / p95 0.23 ms per query (vocab load 14 ms), plus sparse dot + MaxP over 25k passages at mean 1.4 ms / p95 2.1 ms on one core.

I verified a 60-line pure-Python BERT BasicTokenizer + greedy WordPiece against HF `tokenizers` on the opensearch doc-v3-gte tokenizer.json: 0 mismatches on 1,251 lines including accented Spanish names ('Güines, Señor Céspedes'). If `tokenizers` is allowed, Tokenizer.from_file(tokenizer.json) is a drop-in. Note: doc-v3-gte's model code needs trust_remote_code (Alibaba GTE 'NewForMaskedLM', max 8192 positions), but only at build time.

Encode about 25k passages of 256-512 tokens. On the H100's free 8 GB slice that takes a few minutes; on CPU, under an hour. Compute v_j = log(1+log(1+relu(max_over_positions(logits_j)))) per the OpenSearch card, zero the special tokens, prune to the top-k, and quantize to uint8 with a global scale. Query weights: try (a) the shipped idf.json, (b) IDF recomputed on our corpus (Geng's ablation found test-corpus IDF hurts pre-trained models, so test both on validation), and (c) a learned lookup (technique 4).
  - *risks:* Domain shift (MS MARCO -> 1850s prose / noisy OCR) is unmeasured. Inference-free models score stopwords and query meta-words ('part', 'where', 'figures', 'chapter') through the static weights, so tune or zero them. WordPiece splits proper nouns ('Vuelta Abajo' -> vuelta, aba, ##jo), which slightly weakens exact named-entity matching, so keep a word-level BM25 in the fusion. The SPLADE-v3-Doc license is non-commercial. Expansion tokens can increase near-duplicate ties between chapters on the same history.
  - *sources:* ['https://huggingface.co/opensearch-project/opensearch-neural-sparse-encoding-doc-v3-gte', 'https://huggingface.co/opensearch-project/opensearch-neural-sparse-encoding-doc-v2-mini', 'https://arxiv.org/html/2411.04403v2', 'https://huggingface.co/naver/splade-v3-doc', 'https://arxiv.org/html/2403.06789v1', 'https://ar5iv.labs.arxiv.org/html/2305.18494', 'https://arxiv.org/pdf/2104.12016']
  - *confidence:* high
- **Domain-adapted inference-free sparse encoder: fine-tune the doc encoder plus a learned query-token weight table (Li-LSR / IDF-aware) on synthetic slips with near-duplicate hard negatives**
  - *how it works:* Use the filtered synthetic (slip, passage) pairs as training data, Promptagator/GPL-style. Hard negatives are the passages from OTHER docs that BM25 ranks highest for the slip, which are exactly the 'same history told by another book' confounders. Fine-tune a doc-only SPLADE (init from OpenSearch doc-v3-distill or doc-v3-gte). The query side is a 30522-entry learnable scalar per token, Li-LSR style (linear projection of the token embedding -> log(1+relu), initialized from IDF), and query score = sum_t qweight[t] * count_t * doc_impact[t]. Loss: contrastive / KL from a cross-encoder teacher, plus FLOPS/L1 regularization to keep docs sparse. Export the passage impacts (as in technique 3) and the 30522-float query table. Query time is identical to technique 3: tokenize, look up, sparse dot, MaxP. The learned table automatically learns to ignore slip meta-language ('the part where', 'figures for') and to up-weight discriminative Cuban toponyms and names.
  - *expected effect:* Learned query-token tables: Li-LSR Big reaches MS MARCO MRR@10 38.8 and BEIR 48.8 vs SPLADE-v3-Doc 37.8 / 47.0 (+1.0 / +1.8). IDF-aware training (Geng) reaches BEIR 50.35 vs 46.97 (+3.4). In-domain synthetic training: Promptagator's 110M retriever trained ONLY on 8-shot LLM queries averaged 47.8 nDCG@10 on 11 BEIR sets vs BM25 41.8 and MS MARCO-trained SPLADE v2 46.6, and round-trip filtering contributed +2.5. The DSI-QG analogy (model trained on generated queries) reaches NQ320k Hits@1 63.5 vs 39.1 for BM25+docT5query. My estimate for this task: +3-8 Hit@3 over the off-the-shelf doc-only model, concentrated on the near-duplicate confusions. This is a second-phase item, only if phases 1-3 fall short of 0.80.
  - *index size cost:* Same as technique 3 (about 10-20 MB index + 122 KB query table + 231 KB vocab).
  - *query latency cost:* Same as technique 3: about 2-3 ms p95 total on one thread.
  - *query time dependencies:* numpy only (pure-Python WordPiece or `tokenizers`).
  - *build recipe:* Build-time PyTorch on the H100. A 67M DistilBERT-size doc encoder with seq 256, batch 32-64, fp16 and gradient checkpointing fits in about 8 GB. Train on 100-150k slips for 1-3 epochs (under 1-2 GPU-hours). Mine hard negatives with passage-BM25 plus the off-the-shelf sparse model, excluding same-doc passages. Use a teacher from any cross-encoder for distillation margins (optional). Apply Promptagator round-trip filtering (keep a slip if its source doc is in the top-K of a retriever trained on the synthetic data; Promptagator used K=1, but K=3 fits our Hit@3 metric). Early-stop on the held-out synthetic validation and check on the public sample.
  - *risks:* Overfitting to one LLM's slip style, so mix 2 generators and prompts. Catastrophic forgetting of general lexical knowledge, so keep fusion with BM25. Training effort and debugging time are real for a hackathon. The learned table can zero out tokens never seen in synthetic queries, so init from IDF and regularize toward it.
  - *sources:* ['https://arxiv.org/html/2505.01452v1', 'https://arxiv.org/html/2411.04403v2', 'https://arxiv.org/pdf/2209.11755', 'https://arxiv.org/pdf/2206.10128v3']
  - *confidence:* medium
- **Corpus-specific supervised sparse query->doc scorer trained on synthetic slips (linear 'DSI-QG' analogue)**
  - *how it works:* The corpus is closed (1552 docs, no new docs at grading), so learn a direct mapping from query terms to doc ids. Features are stemmed unigrams plus frequent bigrams of the query, hashed or vocab-indexed. The model is a term x doc weight matrix W (vocab x 1552) trained with softmax cross-entropy over the 1552 docs on all synthetic slips (100-150k), plus self-supervised pseudo-queries (random 8-15-word crops and LLM keyword lists from each passage) for coverage. Initialize W from BM25 term-doc weights so it starts as BM25 and learns corrections: down-weighting terms shared by the near-duplicate history chapters and up-weighting doc-specific paraphrase vocabulary. Sparsify by keeping the top 32-64 docs per term (or by L1) and store W in CSR uint8. Query: gather the rows of the query features, sum to a 1552-score vector, and fuse with techniques 1-3. A variant is a fastText-style shallow classifier (hashed n-gram embeddings averaged, dim 64-128, softmax over 1552 labels), stored as npz and evaluated with one 128x1552 matmul.
  - *expected effect:* Indirect evidence only. DSI-QG (a T5 model trained to map generated queries -> doc id, 50 filtered queries/doc) reached NQ320k Hits@1 63.49 / Hits@10 82.36 vs BM25 29.27/60.15 and BM25+docT5query 39.13/69.72. That shows supervised learning on generated queries over a closed corpus of long Wikipedia docs beats expansion by a wide margin. A linear model has far less capacity than T5, so I expect a fraction of that: perhaps +3-10 Hit@3 as a fusion component, mostly from resolving near-duplicate topics. Unverified for this setting.
  - *index size cost:* About 60k features x top-48 docs x 3 bytes (uint16 doc + uint8 w) = about 9 MB. Dense int8 30k x 1552 = 46 MB. The fastText variant (2^18 buckets x 100 dims fp16) is about 52 MB, or about 13 MB at 2^16 buckets.
  - *query latency cost:* Under 0.3 ms (gather about 20 sparse rows and add into a 1552 vector; or a 128x1552 matvec).
  - *query time dependencies:* numpy only.
  - *build recipe:* Train in PyTorch on GPU or CPU (minutes): Adam, CE over 1552 classes, L2 toward the BM25 init, 2-5 epochs, early stop on held-out synthetic slips that come from a DIFFERENT generator or prompt. For the sparse variant, prune and re-fit. sklearn SGDClassifier(loss='log_loss') also works at this scale on the CPU box. Export to npz.
  - *risks:* Memorizes generator style. Docs with few or poor slips get under-trained. Overconfident logits can swamp BM25 in fusion, so calibrate with a temperature and a tuned fusion weight. Gains are unproven outside the DSI-QG analogy, so treat this as an experiment once techniques 1-3 are running.
  - *sources:* ['https://arxiv.org/pdf/2206.10128v3', 'https://arxiv.org/pdf/2209.11755']
  - *confidence:* low
- **Classic impact / expansion models: DeepImpact, uniCOIL, TILDE/TILDEv2, EPIC (assessment against the constraints)**
  - *how it works:* DeepImpact: docT5query-expanded passage -> BERT -> one impact score per unique WORD (first sub-token), 8-bit linear quantized. The query is a plain bag of whole words with weight 1, so the query side is pure-Python whitespace/word tokenization. uniCOIL: per-WordPiece impacts on d2q-expanded passages, but its query weights come from a BERT query encoder, so it is DISQUALIFIED as published. Usable only with binary query weights, which is effectively TILDEv2. TILDE: BERT [CLS] predicts query-likelihood over the full vocab per passage, used for expansion (the top-200 tokens); TILDEv2 stores contextualized exact-match impacts and its query encoder is the BERT tokenizer only, under 1 ms. EPIC: needs BERT at query time for query term importance, so it is DISQUALIFIED unless the query side is replaced by IDF, at which point it is just a weaker doc-only model.
  - *expected effect:* MS MARCO passage dev MRR@10: BM25 0.187, docT5query 0.277, DeepImpact 0.326, uniCOIL+d2q 0.351 (needs a query encoder), uniCOIL without expansion 0.315, TILDEv2 re-ranking BM25 top-1000 0.333 and d2q top-100 0.341, TILDE+BM25 0.269, EPIC+BM25-top100 0.274. The newer doc-only SPLADE family dominates them with inference-free queries (SPLADE-v3-Doc 0.378) and has published BEIR numbers. Recommendation: do not build these; use technique 3/4. DeepImpact's whole-word variant is the only one whose query side needs no WordPiece, which is a minor convenience.
  - *index size cost:* Similar to technique 3 (uint8 impacts). TILDE v1 full-vocab storage is impractical; TILDEv2 is 99% smaller than TILDE.
  - *query latency cost:* Same sparse dot product, about 1-3 ms. TILDE/TILDEv2 were designed as CPU re-rankers under 100 ms.
  - *query time dependencies:* numpy plus WordPiece (TILDEv2) or a word tokenizer (DeepImpact). uniCOIL and EPIC need PyTorch query encoders (disqualified).
  - *build recipe:* Only if needed for an ablation: ielab/TILDEv2-TILDE200-exp and ielab/TILDE on HF (438 MB each, no license tag), or the DeepImpact code from the authors.
  - *risks:* Older MS MARCO-only training. Weaker than SPLADE-doc. The uniCOIL/EPIC query encoders violate the no-PyTorch rule. Licensing is unclear for the ielab checkpoints.
  - *sources:* ['https://arxiv.org/pdf/2106.14807', 'https://arxiv.org/pdf/2104.12016', 'https://arxiv.org/pdf/2108.08513', 'https://huggingface.co/naver/splade-v3-doc']
  - *confidence:* high
- **Leakage-safe synthetic 'slip' validation set for tuning (simulated-query evaluation)**
  - *how it works:* The public sample is small: at n=50, the 95% CI on Hit@3 is about +/-11 points. So generate a separate validation set of 2-5k synthetic slips and use it for all the large tuning decisions: chunk size, k1/b, MaxP vs top-2 aggregation, filter keep-%, fusion weights, query-weight variant. To avoid inflated scores: (a) generate validation slips with a DIFFERENT model and prompt than the expansion slips (e.g. Qwen2.5-32B/72B, or a different temperature and persona prompt, vs 7B for the index), and never append them to the index; (b) sample source positions uniformly through each chapter, matching 'answer buried deep inside', across all source types incl. the OCR Humboldt slice, Country Study and Wikipedia, in proportion to the expected hidden mix; (c) include ToT-style 'from memory' instructions (no titles or names, paraphrase, slight imprecision such as '1890s' instead of 1894) as in TREC ToT query simulation; (d) report the public-sample Hit@3 next to it for every config, and only trust config changes that move BOTH in the same direction. Also track 'confuser' stats: for each miss, is the top-1 a same-topic chapter from another book? That tells you whether to work on specificity (filters, hard negatives) or recall (coverage).
  - *expected effect:* No direct accuracy gain; this reduces tuning variance and over-fitting to the tiny public sample. Evidence that simulated vague queries rank systems like real ones: LLM-elicited tip-of-the-tongue queries vs community queries gave Kendall tau 0.72-0.76 / Pearson 0.90-0.92 for Movies, and tau 0.57-0.70 / Pearson 0.72-0.91 for Landmark and Person. TREC ToT 2024/2025 adopted synthetic queries for evaluation. Promptagator tuned its filter K on held-out data and found K=1 best.
  - *index size cost:* None (build-time only).
  - *query latency cost:* None.
  - *query time dependencies:* None.
  - *build recipe:* Use the same vLLM setup. Prompt: 'You read this chapter long ago. Write N one-line notes (6-20 words) you'd hand to a librarian to find THIS passage, imitating these examples: <public slips>. Do not use titles or exact names of books or articles; describe people by role; paraphrase; mention one detail unique to this passage; numbers may be approximate.' Use about 2-3 slips per sampled passage and 1-3 passages per doc. Hold out entire validation generations from the index. Optionally build a 'validation index' that also excludes the expansion slips of the validation passages, to get a pessimistic bound; the truth lies between the two.
  - *risks:* Synthetic validation shares the generator's biases, so a config can win on synthetic and lose on hidden. Mitigate by using a different generator and by requiring agreement with the public sample. Using the public slips as few-shot examples for BOTH the expansion and validation generators correlates the two; vary the exemplar subsets.
  - *sources:* ['https://arxiv.org/html/2502.17776v2', 'https://arxiv.org/pdf/2601.20671', 'https://arxiv.org/pdf/2209.11755', 'https://arxiv.org/html/2309.08541v2']
  - *confidence:* medium

### tiny-dense

**Top recommendation:** Build the asymmetric passage-level dense index first, and fuse it with BM25. Doc side, at build time: OCR-clean the Humboldt chapters, chunk every doc into overlapping windows of about 160 tokens (stride 80, title-prefixed), and embed them with Snowflake arctic-embed-m-v1.5. It fits easily in the 8 GB of free GPU. Truncate to 256 dims (MRL) and store int8 with a fixed +/-0.3 range: 99% of the full model's 55.1 MTEB retrieval kept, at 256 B/passage, about 15-25 MB for 60-100k passages. Load once into fp32 RAM, score exactly with a numpy matvec plus a per-doc max (MaxP), then fuse with BM25 by convex combination. Measured on this Xeon, single thread: 8 ms at 50k x 256 and 16 ms at 100k x 256 (p50). Query side: if requirements.txt has onnxruntime, use MongoDB/mdbr-leaf-ir as the query encoder. It is a 23 MB int8 ONNX model, distilled from arctic-m-v1.5 into the same space, scoring 54.03 BEIR in asymmetric mode against 51.7 for bge-small and 41.9 for MiniLM, at about 6 ms p50 / 9 ms p95 measured. Verify its int8 export against fp32 (target cosine > 0.995) and check that truncating to 256 dims holds up on the public sample. If only numpy is allowed, train a static lookup-table query encoder: Model2Vec distill with corpus vocabulary, then tokenlearn, then MNRL/MSE alignment to the frozen arctic passage vectors on LLM-written slips with same-topic hard negatives. It runs in 0.2 ms, about 7 MB, with a pure-Python WordPiece tokenizer. Why this first: it moves all model quality to build time, where compute is free, it fits a 40-50 MB total budget (about 25 MB with the static query side), it keeps p95 at roughly 10-25 ms, and it directly attacks the two stated difficulties, paraphrased slips and answers buried in long chapters. If the latency limit turns out to be about 10 ms, add a BM25 or doc-vector shortlist (top 50 docs) before the passage scoring. If the size limit is about 20 MB, drop to int4 or 128-d and use the static query encoder.

#### Techniques

- **Asymmetric dual encoder: big MRL teacher embeds passages at build time, a tiny encoder embeds queries**
  - *how it works:* Only the query has to be encoded at query time, so the two sides do not need the same model. Build time: split every doc into overlapping passages of about 128-200 tokens, then embed them with a strong teacher whose vectors truncate cleanly. Snowflake/snowflake-arctic-embed-m-v1.5 (109M, 768-d, CLS pooling) is the one to use: it was trained to truncate to 256 dims (Matryoshka, MRL) and to quantize with one fixed range. Truncate to 256 dims, re-normalize, and store int8 with the uniform range +/-0.3 (or int4 with +/-0.18). Query time has two options. (a) MongoDB/mdbr-leaf-ir (6 layers x 384 hidden, 23M params), which was distilled from arctic-m-v1.5 so its 768-d output lands in the teacher's space. Run its int8 ONNX transformer, apply its 384->768 Dense layer in numpy (a 1.2 MB weight), take the first 256 dims and normalize. Queries need the prefix 'Represent this sentence for searching relevant passages: '. (b) Numpy only: train our own static lookup-table query encoder (see the custom static technique) to regress the teacher's 256-d query embeddings. Scoring is the same either way: q @ P.T over all passages, then the max per doc (MaxP), then fusion with BM25.
  - *expected effect:* Published numbers: mdbr-leaf-ir in asymmetric mode (leaf queries, arctic-m-v1.5 docs) scores 54.03 BEIR nDCG@10. That beats symmetric leaf at 53.55, arctic-embed-s at 51.98, bge-small at 51.65, arctic-xs at 50.15, MiniLM-L6 at 41.95 and BM25 at 41.14 on the same table, and it is about 98% of the teacher's 55.14. Doc-side compression barely costs anything: arctic-m-v1.5 at 256-d int8 scores 54.2 (99% retained, 256 B/vector), and at 256-d int4 it scores 53.7 (98%, 128 B/vector). Supporting results: query-encoder distillation by embedding alignment keeps 92.5% of the full dual encoder with a 2-layer student and 86.1% with a 1-layer one (Wang & Lyu 2023), and EmbedDistill reports 95-97% at 1/10 size. I have no Hit@3 number for this corpus. My guess is that it beats any symmetric tiny model by a few points, because the passage side gets base-model quality for free.
  - *index size cost:* Passage vectors at 256-d int8 cost 256 B each: 50k passages = 12.8 MB and 100k = 25.6 MB (int4 halves that). Query side (a): leaf-ir int8 ONNX about 23 MB (model_quantized.onnx_data is 22.95 MB), plus the Dense layer at 1.2 MB and tokenizer.json at 0.7 MB. Query side (b): a static table of about 25-30k tokens x 256 int8 is 6-8 MB. Total is about 37-50 MB for (a) and 20-35 MB for (b), before the BM25 index.
  - *query latency cost:* Measured on this box (Xeon Silver 4214 @2.2 GHz, onnxruntime 1.32, intra_op=1, pinned to one core, shared and noisy). Query side (a): a 6-layer x 384 int8 ONNX model (same architecture as leaf-ir and arctic-xs) took p50 6.2 ms and p95 8.6 ms for 14-24 token queries including tokenization; the fp32 ONNX took p50 11.9 ms and p95 17 ms. Query side (b): a static lookup took p50 0.2 ms and p95 0.4 ms. Scoring: an fp32 matvec plus the per-doc max (np.maximum.reduceat) took p50/p95 8.0/10.6 ms at 50k x 256 and 16.1/16.9 ms at 100k x 256.
  - *query time dependencies:* (a) onnxruntime plus numpy, and `tokenizers` or a pure-Python BERT-uncased WordPiece (about 40 lines: lowercase, NFD accent strip, punctuation split, greedy longest match). Its output must be checked for exact parity with tokenizers. (b) numpy only, plus that same pure-Python WordPiece or a word-level vocab.
  - *build recipe:* 1) Chunk docs: about 160-token windows with stride 80, prefixing each chunk with its doc title. Clean the Humboldt OCR first; any LLM or regex can do this at build time. 2) Embed passages with arctic-embed-m-v1.5 in sentence-transformers on the H100. 110M params fits easily in the 8 GB that is free, and 100k passages take minutes. 3) Truncate to 256, normalize, and quantize with np.clip(np.round(x/0.3*127),-127,127).astype(int8). 4) Export leaf-ir to ONNX: it ships onnx/model_quantized.onnx, or re-export with optimum. Check that the int8 output has cosine > 0.995 against fp32 on about 1k queries. 5) Optionally fine-tune the query encoder alone, with the doc side frozen, on LLM-written 'slips' for corpus passages. Use MNRL against the frozen teacher passage vectors plus hard negatives from other docs on the same topic, then re-export. Compute: under 1 GPU-hour outside of query generation.
  - *risks:* leaf-ir in asymmetric mode was evaluated at the full 768 dims. Whether truncating it to 256 dims behaves like the teacher's MRL truncation is plausible but untested, so check it on the public sample or keep 384-512 doc dims. The int8 export quality depends on the exporter: in my test Xenova's all-MiniLM-L6-v2 int8 reached only cosine 0.94-0.98 against fp32, while Snowflake's arctic-xs int8 reached 0.998 and Xenova's bge-small int8 0.997. The query prefix adds about 10 tokens, so about 1-2 ms. If onnxruntime is not in requirements.txt, option (a) is ruled out.
  - *sources:* ['https://huggingface.co/MongoDB/mdbr-leaf-ir', 'https://huggingface.co/Snowflake/snowflake-arctic-embed-m-v1.5', 'https://arxiv.org/abs/2306.11550', 'https://arxiv.org/abs/2301.12005', 'local benchmark: /tmp/claude-1003/-mnt-data-projects-Chinese-spy-sigmoid-hack/b47426bd-f0d3-4374-bd91-a107ea984daa/scratchpad/bench/bench_enc.py, bench_score.py, cos.py']
  - *confidence:* medium
- **Off-the-shelf static embeddings (Model2Vec potion-*, static-retrieval-mrl-en-v1): numpy only**
  - *how it works:* Encoding is a table lookup. Tokenize with BERT-uncased WordPiece and no special tokens, take the mean of E[ids], then L2-normalize. There is no attention or context. The candidates and their measured shapes: potion-base-8M is 29,528 x 256 (bge-base vocab, distilled then trained with tokenlearn); potion-retrieval-32M is 63,091 x 512, a WordPiece vocab extended with whole words, fine-tuned for retrieval with MNRL and Matryoshka dims 32-512; static-retrieval-mrl-en-v1 is 30,522 x 1024, trained from scratch with contrastive MNRL and Matryoshka loss. Use them on the passage side too, with short chunks (about 64-128 tokens), because mean-pooling a long passage averages its signal away. Score with matvec plus the per-doc max, then fuse with BM25.
  - *expected effect:* NanoBEIR nDCG@10: static-retrieval-mrl 0.503 (0.482 at 256-d, 0.462 at 128-d), potion-base-8M 0.442, BM25 0.452, all-MiniLM-L6 0.562, bge-small 0.627. MTEB retrieval: potion-retrieval-32M 35.06, static-retrieval-mrl 34.95, potion-base-32M 32.67, potion-base-8M 31.11, potion-base-4M 28.43, potion-base-2M 22.99, MiniLM-L6 42.92. Static is roughly BM25-level on its own: 0-5 points better on general benchmarks. Its errors are bag-of-words like BM25's, so the expected gain in a hybrid is modest; my estimate is +1-4 Hit@3 points. Domain words split badly: in my test potion tokenized 'Matanzas' as mata/##nza/##s and 'Abajo' as aba/##jo, and OCR noise such as 'tob4cco' as to/##b/##4/##cco, so names and OCR text get poor vectors.
  - *index size cost:* potion-base-8M: 30 MB fp32, 15 MB fp16, 7.5 MB int8. potion-retrieval-32M: 129 MB fp32, 32 MB at int8 x 512, 16 MB at int8 x 256 (MRL-trained). static-retrieval-mrl: 125 MB fp32, 7.8 MB at 256-d int8. Pruning the vocab to tokens seen in the corpus plus common query words (about 20-25k) cuts this a further 2-3x. ### fusion-rerank

**Top recommendation:** Build this first, all in numpy. (1) Score windows of about 200 words with BM25, plus the dense track's encoder, and aggregate to docs by MaxP. Keep the 2nd-best window and whole-doc BM25 as extra signals. (2) Fuse with a theoretical-min-max convex combination over all 1552 docs, alpha tuned on synthetic slips (Bruch et al.: CC beat RRF on all 9 test sets by 1.5-3 nDCG points). Keep weighted RRF only as a sanity baseline. (3) Put a listwise logistic learning-to-rank model with about 15 features on the top 30-50 docs. Include the near-duplicate signals: candidate-local IDF, number/decade matches, phrase/proper-noun hits, a metadata/LLM-descriptor field, and kind one-hots with kind x signal interactions for the OCR and old-prose slices. Train it on 5-20k LLM-generated, LLM-relabeled slips in the public sample's style and source mix, and use the public sample only for paired-bootstrap validation. Even with 100 public questions, Hit@3 has about a 4-point standard error, so tuning on it alone would overfit. This stack costs about 5-10 ms of single-thread CPU plus query embedding and a few MB on top of the signal indexes, so it should fit the 10-200 ms and 10-200 MB budgets. Try a LambdaMART GBDT (dumped to arrays, about 1 ms) only if it beats the linear model on held-out synthetic data without losing on the public sample. #### Techniques

- **Passage-window scoring with max-passage (MaxP) aggregation, plus a doc-level score kept as its own feature**
  - *how it works:* Split every doc into windows of about 150-250 words. Use about 50% overlap for the dense vectors. Use non-overlapping or 25%-overlap windows for BM25, to keep postings small. Store windows sorted by doc, with a doc_start offset array. At query time, score every window with each signal. For BM25 that is numpy bincount over the postings of the query terms, with minlength=n_windows. For dense it is one matvec against the window matrix. Turn window scores into doc scores with np.maximum.reduceat(scores, doc_start), which gives MaxP. Add the 2nd-best window score, or a soft-max: log-sum-exp with a temperature tuned on synthetic queries. Also keep a whole-doc BM25 score (tuned b) and the doc title/metadata score as separate features. Callan 1994 found that combining doc and best-passage evidence beats either one alone. Scoring all 1552 docs this way is exhaustive, so no candidate cutoff is needed before fusion. Return the best window id too: later stages (disambiguation features, an optional reranker) reuse it.
  - *expected effect:* Pyserini MS MARCO-doc, BM25 at default k1=0.9/b=0.4: whole doc 0.2299 MRR@100 vs segmented MaxP 0.2684 (+17% rel). DL19 nDCG@10 is 0.5176 vs 0.5302. With tuned BM25 the two tie (0.2767 vs 0.2756), so for BM25 alone the gain mostly makes up for poor length normalization. Callan 1994, reported second-hand by Sarwar et al. 2017: ranking by the best passage is up to 20% better than doc scores. For dense signals, MaxP is close to mandatory here. Encoders truncate at 256-512 tokens (FirstP), and the task says the answer is usually buried deep in a chapter, so a whole-chapter embedding or FirstP misses it. Dai & Callan (SIGIR 2019) found MaxP beat FirstP for long docs. Expect this to be the largest single structural gain in the pipeline, especially on the dense side.
  - *index size cost:* Scales with corpus words, so assume 3-8M words. With non-overlapping 200-word windows that is about 15-40k windows, and about 1-3M unique (term, window) postings. Stored as uint16 window id plus uint8 tf at 3 bytes each, that is about 3-9 MB, or 2x with 50% overlap. Dense window matrix: n_windows x d x bytes. For example, 40k x 256 x 1 (int8) = 10 MB, or 40k x 384 x 2 (fp16) = 31 MB. Offsets and metadata are under 1 MB.
  - *query latency cost:* BM25 over windows: about 1-3 ms for 5-15 query terms (bincount over roughly 50-150k gathered postings). Dense matvec over 40k x 256 as fp32 in memory: about 1-3 ms. Keep it fp32 or fp16 upcast at load time, because numpy int8 matmul does not use BLAS. reduceat MaxP: about 0.1 ms. Total about 3-6 ms, excluding query embedding.
  - *query time dependencies:* numpy only. scipy.sparse is optional and not needed.
  - *build recipe:* CPU box. Tokenize: lowercase, keep numbers as tokens, light stemming or none, and keep a stopword list. Build windows and postings arrays and save them as .npy. Embed windows with whichever dense encoder the dense track picks, on the H100. Tune window size (150/250/400), stride, and MaxP vs top-2 soft aggregation on synthetic slips (see the synthetic-slips technique). Expect minutes of compute.
  - *risks:* Short windows lose context: a slip that summarizes a whole scene can span 2 windows, and overlap or top-2 aggregation mitigates this. Heavy overlap doubles BM25 postings and size. On long chapters, MaxP favors docs with one lucky window, so keep the doc-level and 2nd-best features to temper it. OCR docs (Humboldt) yield garbled windows that score low on every signal, which needs per-source calibration.
  - *sources:* ['https://castorini.github.io/pyserini/2cr/msmarco-v1-doc.html', 'https://arxiv.org/abs/1905.09217', 'https://www.scitepress.org/PublishedPapers/2017/65028/65028.pdf']
  - *confidence:* high
- **Hybrid lexical+dense fusion by convex combination with theoretical-min-max normalization (TM2C2), weighted RRF kept as a fallback**
  - *how it works:* Score all 1552 docs per signal, using the MaxP doc scores above. Normalize per query with theoretical min-max: s' = (s - m_theory) / (max_q(s) - m_theory). For BM25, m_theory = 0. For cosine, use -1, or the observed global minimum from build time. Fuse with fused = alpha*dense' + (1-alpha)*bm25'. With more than 2 signals, use a weight simplex: doc-BM25, window-BM25, window-dense, title/metadata field and others. Tune alpha on synthetic slips with a grid of 0..1 in 0.05 steps, optimizing Hit@3 directly. Baseline and fallback is weighted RRF: sum_i w_i / (k + rank_i), with k=60 as the default. The paper shows RRF is not parameter-free, and lexical and semantic lists want different k. Return the top 3, or the top 30-50 as candidates for the learning-to-rank stage. Fusion over a closed set of 1552 docs avoids the 'missing from one list' problem that RRF handles poorly with truncated lists.
  - *expected effect:* Bruch, Gai & Ingber (TOIS 2023), NDCG@1000 with BM25 + all-MiniLM-L6-v2, CC alpha=0.8 vs RRF(60) vs best single signal. MS MARCO: 0.454 / 0.425 / 0.441. NQ: 0.542 / 0.514 / 0.505. FiQA: 0.496 / 0.464 / 0.467. DBPedia: 0.512 / 0.489 / 0.425. FEVER: 0.744 / 0.721 / 0.689. SciFact: 0.753 / 0.730 / 0.698. CC beat RRF on all 9 datasets, by 1.5-3 points. alpha in [0.6, 0.8] improved consistently, and alpha converged with under 5% of the training data. Tuned RRF parameters did not transfer across domains: NDCG 'swings wildly'. A per-query oracle alpha adds another 0.04-0.10, which shows the headroom for learning-to-rank. Wang, Zhuang & Zuccon (ICTIR 2021): ANCE+BM25 at alpha=0.5 gives DL19 nDCG@10 0.6875 vs 0.6452 (+6.6%), and oracle alpha gives 0.7441 (+15.3%). RepBERT+BM25 at alpha=0.5 raises MS MARCO MRR@10 from 0.3040 to 0.3222. OpenSearch: on 6 BEIR sets, RRF averaged 3.86% lower NDCG@10 than min-max + arithmetic mean. Vespa: on 13 BEIR sets, a BM25+ColBERT min-max linear hybrid averaged 0.481 vs 0.453 for BM25 and 0.363 for ColBERT. Expect hybrid over the best single signal to add roughly +3-10 Hit@3 points here, since lexical rare words and dense paraphrase cover different slips.
  - *index size cost:* None beyond the signals: a few floats of weights in a JSON file.
  - *query latency cost:* Under 0.5 ms: normalization plus a weighted sum over 1552 docs, with argpartition for the top-k. RRF needs one argsort per signal over 1552 docs, about 0.1 ms each.
  - *query time dependencies:* numpy only
  - *build recipe:* Grid-search alpha (and the RRF k per list) on several thousand synthetic slips. Confirm on the public sample with a paired bootstrap. Check that the tuned alpha is stable across 5 folds of the synthetic set.
  - *risks:* Min-max uses the per-query maximum, so one outlier doc (a very long Wikipedia article with many keyword hits) compresses everyone else. Theoretical-min or z-score normalization reduces this, and Bruch shows the normalization choice matters little once alpha is tuned. Score distributions differ by source (19th-century prose, modern Wikipedia, OCR), so one global alpha can be biased against a slice (see the calibration technique). RRF throws away the margin information that tells near-duplicates apart.
  - *sources:* ['https://arxiv.org/abs/2210.11934', 'https://arxiv.org/html/2210.11934v2', 'https://arvinzhuang.github.io/files/shuai2021interpolateDR.pdf', 'https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf', 'https://opensearch.org/blog/introducing-reciprocal-rank-fusion-hybrid-search/', 'https://blog.vespa.ai/improving-zero-shot-ranking-with-vespa-part-two/']
  - *confidence:* high
- **Learning-to-rank over about 15 hand features: listwise logistic or linear model first, a small LambdaMART GBDT second, both evaluated in numpy**
  - *how it works:* Take the top 30-50 docs from the fused score; recall@50 should be about 0.99, so verify it. For each (query, doc) compute a feature vector: (1) best-window BM25, (2) 2nd-best-window BM25, (3) whole-doc BM25, (4) best-window dense cosine, (5) mean of top-3 window cosines, (6) title/metadata-field BM25 and cosine, (7) the fused CC score. For (1)-(7), add the query-normalized versions: value / max over candidates, rank, and gap to the top candidate. (8) IDF-mass coverage: the fraction of the query's summed IDF matched in the best window. (9) Number/year matches (see the disambiguation technique). (10) Proper-noun/bigram phrase matches. (11) candidate-local IDF overlap. (12) char-3gram cosine, which helps the OCR slice. (13) log doc length and number of windows. (14) one-hot source/kind (wiki, PG book, Country Study, OCR Humboldt). (15) kind x signal interactions, needed by the linear model only. (16) log P(kind|query) from a query classifier. Model A: listwise softmax cross-entropy (one positive per query) with L2, about 30 weights, trained in numpy or scikit-learn at build time. It is equivalent to logistic regression over candidates. Model B: LightGBM objective=lambdarank, eval_at=3, lambdarank_truncation_level of about 10, num_leaves 7-15, at most 200-300 trees, min_data_in_leaf 50 or more, feature_fraction 0.8, plus monotone_constraints=+1 on the core relevance signals to limit overfitting. Export with booster.dump_model() into flat arrays (split_feature, threshold, left, right, leaf_value). Evaluate it by vectorized level-wise traversal: node = root; repeat depth times: node = where(x[f[node]] <= thr[node], left, right) over a (trees x candidates) matrix. Keep B only if it beats A on held-out synthetic data and does not lose on the public sample.
  - *expected effect:* No paper directly measures few-feature learning-to-rank against tuned CC on a corpus this small. The bounds: Bruch's per-query oracle alpha shows 0.04-0.10 NDCG headroom over the best global alpha, and per-query adaptivity is exactly what learning-to-rank buys. The extra features (priors, numbers, phrases, calibration) carry information neither CC signal has. My estimate is +1-5 Hit@3 points over the tuned 2-3 signal CC, more if source priors or number matching matter for the hidden slips. Training on a ranking metric truncated at 3 also targets Hit@3 directly, unlike tuning alpha by NDCG. Treat the gain as unproven until synthetic and public cross-validation confirms it.
  - *index size cost:* Linear model: under 1 KB. GBDT with 300 trees x 15 leaves: about 100-200 KB as .npy arrays (JSON is larger). Small per-doc feature tables: about 50 KB.
  - *query latency cost:* Feature computation for 50 candidates: about 1-3 ms, since most of it reuses arrays already computed. Linear model: about 10 us. GBDT numpy level-wise traversal of 300 trees x 50 candidates x depth 4-6: about 0.3-1 ms. A Python loop per tree would be about 5 ms, so vectorize.
  - *query time dependencies:* numpy only. LightGBM is needed only at build time; the trees are dumped to arrays.
  - *build recipe:* Build time: about 5-20k synthetic slips with labels (see the synthetic-slips technique). Compute candidates and features with the same code main.py uses, so there is no train/serve skew. Train with LightGBM or sklearn on CPU in seconds to minutes. Use 5-fold grouped cross-validation by source doc, so slips from the same doc never sit in both train and test. Select on held-out synthetic Hit@3, then confirm on the public sample.
  - *risks:* Overfitting to the synthetic slips' style, since an LLM writing slips leaks its own phrasing habits. Feature leakage if a doc2query field is built from the same generated slips used for training: use disjoint generations. Kind priors learned from a synthetic set whose source mix does not match the hidden set's. A GBDT that is unstable on a 50-100-question public sample. Keep the linear model unless the GBDT win is clear.
  - *sources:* ['https://arxiv.org/html/2210.11934v2', 'https://lightgbm.readthedocs.io/en/latest/Parameters.html', 'https://www.microsoft.com/en-us/research/publication/from-ranknet-to-lambdarank-to-lambdamart-an-overview/']
  - *confidence:* medium
- **Near-duplicate disambiguation features: rare-term, candidate-local IDF, numbers/decades, phrase/proper-noun and metadata-field matching**
  - *how it works:* Many docs tell the same history, so dense similarity and topical BM25 score them almost equally. The slip was written from one doc's passage, and what usually survives a from-memory paraphrase is the distinctive tokens: a place (Matanzas, Vuelta Abajo), a number or decade, an odd word ('rolled leaves'), a role ('the traveller', 'the consul'). Features: (a) Candidate-local IDF. Among the top K of about 10-20 candidates, compute df_local(t) = number of candidates whose text (and separately, whose best window) contains query term t. Weight w(t) = idf_global(t) * log((K - df_local + 0.5)/(df_local + 0.5) + 1). The score is the sum of w(t) over terms present. Terms every candidate shares drop to about 0, and terms only one candidate has dominate. Doc-level term presence comes straight from doc postings. (b) Numbers. At build time, extract every number and year per window (and per doc) into sorted int arrays. At query time, parse numbers, expand '1890s' to 1890-1899, 'the sixteenth century' to 1500-1599, and normalize '1,000' and 'one thousand'. Count exact and range hits in the best window and the doc. (c) Phrases and proper nouns. Build a bigram postings index restricted to bigrams with df at most some cap, plus a dictionary of capitalized multiword names mined from the corpus. Score phrase hits in the query, which handles lowercase slips through dictionary lookup. (d) Metadata/descriptor field. For each doc, store title, book title, author, chapter heading and an LLM-written 1-2 sentence 'who/where/when' descriptor (for example 'first-person account by an American visitor, 1850s, tobacco vegas of Pinar del Rio'). Index it as its own BM25 field and dense vector, so that 'the traveller who described...' matches travel-account docs. (e) Proximity: the span of matched query terms in the best window. All of these go into the learning-to-rank model rather than being hand-weighted.
  - *expected effect:* EntityQuestions (Sciavolino et al. 2021): DPR averaged 49.7% top-20 accuracy vs BM25 at 72.0%, and multi-dataset DPR reached only 56.7%. Dense encoders lose on rare entities, so the rare-term lexical signal has to drive the final pick among near-duplicates. Metzler & Croft 2005 (MRF sequential dependence) found that term-dependency (phrase and proximity) features give significant gains, largest on big web collections; the paper's percentages were not checked here. Expected here: gains concentrate on the near-duplicate slips that are the stated main difficulty. My estimate is +2-6 Hit@3 overall, with most of the lift on Hit@1, which also protects Hit@3 when 3 or more near-duplicates compete. Number matching should nearly settle 'figures for X in the 1890s'-type slips. Low-to-medium confidence on the size.
  - *index size cost:* Numbers per window: about 0.2-1 MB. Restricted bigram postings: about 3-10 MB, depending on the df cap. Proper-noun dictionary: under 1 MB. Descriptor field for 1552 docs x about 60 words: under 1 MB, plus 1552 dense vectors (under 1 MB).
  - *query latency cost:* About 1-3 ms in total for K=20-50 candidates: set lookups, small numpy intersections, and regex number parsing on the query.
  - *query time dependencies:* numpy plus Python re and json, all standard library.
  - *build recipe:* CPU: number extraction with regex, bigram counting, and capitalized n-gram mining with a df filter. Descriptors: one LLM call per doc, 1552 calls. Qwen 72B or 32B AWQ needs about 20-40 GB of GPU memory, so wait for free memory, or use Qwen2.5-7B-AWQ, which fits in 8 GB, for descriptors. Ablate each feature on synthetic slips: keep a feature only if its fold-averaged gain is positive.
  - *risks:* Candidate-local IDF is noisy when K is small or the candidates are from one book (adjacent chapters). OCR noise breaks exact number and name matching in Humboldt docs, so add OCR-tolerant variants such as char n-grams and digit-normalization ('1S90' to '1890' via common OCR confusions). LLM descriptors can hallucinate, so keep them short and factual and verify a sample. Bigram index size grows quickly without a df cap.
  - *sources:* ['https://arxiv.org/abs/2109.08535', 'https://maroo.cs.umass.edu/pub/web/getpdf.php?id=531', 'https://arxiv.org/abs/2210.11934']
  - *confidence:* medium
- **Per-source score calibration and a query-conditioned source/kind prior**
  - *how it works:* The corpus mixes 4 kinds of text. Each produces systematically different raw scores. Wikipedia's modern vocabulary inflates dense cosines from web-trained encoders. 19th-century prose has archaic spelling. OCR text deflates both BM25 and dense. Fix 1, calibration: at build time, for each (source kind, signal), fit a 2-parameter Platt map, or isotonic regression, from the raw normalized score to P(doc is the answer | score), using synthetic slips. At query time, apply the per-kind affine map before fusion. Equivalently, give the learning-to-rank model kind x signal interaction features. Fix 2, prior: (a) a static log-prior per kind, estimated from the public sample's answer mix; (b) a query-conditioned prior. Train a multinomial logistic regression on TF-IDF of the slip text to predict the gold doc's kind (4 classes) or source (about 25 classes), on synthetic slips. 'The traveller who...' points to travel books; 'sugar figures for Matanzas' points to reports, the Country Study or Wikipedia. Feed log P(kind|q) as a learning-to-rank feature. This is federated-search resource selection (CORI/ReDDE style) applied to a single index.
  - *expected effect:* There is no direct benchmark for this exact setup. The mechanism matters most when one slice is systematically under-scored, as with OCR, where a raw fused score can push the right Humboldt chapter below a cleaner Wikipedia near-duplicate. My estimate: +1-3 Hit@3 overall, with larger gains on the OCR and book slices. If the hidden set's source mix differs from the training mix, a static prior can hurt, so prefer the query-conditioned version.
  - *index size cost:* Calibration: about 4 kinds x 5 signals x 2 floats, negligible. Query classifier: TF-IDF vocabulary of about 30k terms x 4-25 classes in float16, about 0.25-1.5 MB, which can share the BM25 vocabulary and IDF.
  - *query latency cost:* Under 0.3 ms: a sparse dot product of query terms against the class weight matrix, plus affine maps.
  - *query time dependencies:* numpy only
  - *build recipe:* Use the same synthetic slip set as the learning-to-rank model. Fit with sklearn LogisticRegression at build time and save the weights as .npy. Generate synthetic slips in the same source mix as the public sample, or the priors will be biased.
  - *risks:* Overfitting to the prior: the model may learn 'always pick Wikipedia' if Wikipedia dominates the training slips (955 of 1552 docs are Wikipedia). The query-kind classifier can latch onto the synthetic generator's style instead of content. Validate on the public sample by kind.
  - *sources:* ['https://arxiv.org/html/2210.11934v2', 'https://arxiv.org/abs/2403.20327']
  - *confidence:* low
- **Tiny cross-encoder reranker (TinyBERT-L2 / MiniLM-L2), domain-adapted and used as one learning-to-rank feature on the best window of the top 5-8 docs, only if latency and requirements allow**
  - *how it works:* After learning-to-rank, take the best window of each of the top 5-8 docs. Crop it to about 96-128 tokens centered on the densest query-term region, and score (query, window) with an int8 ONNX cross-encoder. Pre-tokenize all windows into int16 WordPiece ids at build time, so only the query is tokenized at query time; a pure-Python greedy WordPiece over vocab.txt takes about 0.1 ms. Feed the CE logit to the learning-to-rank model as an extra feature rather than reranking by it alone. Off-the-shelf MS MARCO CEs are worse than BM25 zero-shot on long, out-of-domain text. If used, fine-tune at build time on synthetic slips: positive = the generating window, hard negatives = best windows of near-duplicate docs. Use MarginMSE distillation from a strong teacher (bge-reranker-v2-m3 or Qwen judgments). Then export to ONNX and apply dynamic int8 quantization. Optional gating: run the CE only when the learning-to-rank margin between ranks 2 and 4 is small. Gating only helps p95 if no more than about 5% of queries trigger it.
  - *expected effect:* Off the shelf: MS MARCO dev MRR@10 is 32.56 for TinyBERT-L2, 34.85 for MiniLM-L2, 37.70 for L4, 39.01 for L6 and 39.02 for L12 (sbert). Zero-shot on 8 BEIR sets (Covid, NFCorpus, Touche, DBPedia, SciFact, Signal, News, Robust04), reranking BM25 top-100: FlashRank TinyBERT averages 42.24 vs BM25 43.42, which is WORSE than BM25. On the long-doc sets: News 37.53 vs 39.52, Robust04 41.37 vs 40.70. MiniLM-L12 averages 46.41 (+3.0). On 11 BEIR sets, MiniLM-L6 rerank averages 0.532 vs BM25 0.437, with most of the gain on QA-style sets. Promptagator: a reranker trained on LLM-generated in-domain queries adds about 5.0 nDCG over its retriever. Expect off-the-shelf TinyBERT to give about 0 or a negative change vs a good hybrid with learning-to-rank. An in-domain fine-tuned L2 model used as a feature might add +1-4 Hit@3. This is unproven: validate before shipping.
  - *index size cost:* int8 ONNX: TinyBERT-L2 4.5 MB, MiniLM-L2 15.8 MB, L4 19.5 MB, L6 23.2 MB; fp32 is 17.6/62.5/76.8/91.0 MB. Pre-tokenized windows: about 2 bytes per token, about 10-16 MB for 5-8M tokens. Cheaper: store only the ids of crop-able windows, or tokenize the cropped window at query time if `tokenizers` is allowed.
  - *query latency cost:* Measured by me: onnxruntime 1.32, 1 intra-op thread, on a Xeon Silver 4214 @ 2.2 GHz (Cascade Lake, AVX-512 VNNI), median of 5-15 runs, random ids. Single-thread numpy BLAS reached 42-44 GFLOP/s, so the core was not starved despite the shared box. Per pair: TinyBERT-L2 int8-VNNI 1.4 ms @64 tok / 3.1 ms @128; fp32 2.0 / 4.3 ms @64/128 and 10.4 ms @256. MiniLM-L2 int8-VNNI 6.1 ms @64 / 13.7 ms @128 (fp32 12.8 / 27.6). MiniLM-L4 int8-avx2 45 ms @128 (fp32 53). MiniLM-L6 int8-VNNI 17.7 ms @64 / 40.9 ms @128 (fp32 38.8 / 81). The portable quint8_avx2 build gave only 5-15% over fp32 on this CPU; the VNNI build gave about 2x. Session load: 0.1-0.37 s. Pure-numpy re-implementation of the same shapes: H128 L2 4.6 ms/pair @64 and 10.2 ms @128; H384 L2 29 ms @64 and 118 ms @128. So without onnxruntime, only TinyBERT-L2 is feasible. Budget: TinyBERT int8, 8 pairs x 128 tok, about 25 ms; MiniLM-L2, about 110 ms. L4 and L6 are out for any budget under 200 ms.
  - *query time dependencies:* onnxruntime, which must be in the grader's requirements.txt, or a pure-numpy BERT forward with .npy weights (TinyBERT-L2 only, about 3x slower than ORT). The query tokenizer can be pure Python over vocab.txt; `tokenizers` is optional. No PyTorch at query time.
  - *build recipe:* Fine-tune with sentence-transformers CrossEncoder on GPU. TinyBERT-L2 trains in under 8 GB, in minutes to an hour, on about 50-200k (query, positive, hard-negative) triples built from synthetic slips. Teacher scores come from bge-reranker-v2-m3 (fits in 8 GB). Export with optimum or torch.onnx, then onnxruntime.quantization.quantize_dynamic, building both an avx2 variant and an avx512_vnni variant. Pick the variant at load time with a 50 ms micro-benchmark, since the grader's CPU is unknown. Check that int8 does not hurt the score on held-out slips.
  - *risks:* Biggest risk: it adds 25-110 ms to p95 for a gain that may not appear, since off-the-shelf small CEs underperform BM25 zero-shot on BEIR. It is disqualified if onnxruntime is not allowed and the limit is tight. int8 kernel speed is CPU-specific, and an old grading machine without VNNI erases the 2x. A 128-token crop can cut out the clue. In-domain fine-tuning on synthetic slips can overfit their style.
  - *sources:* ['https://www.sbert.net/docs/cross_encoder/pretrained_models.html', 'https://arxiv.org/html/2508.16757', 'https://arxiv.org/html/2304.09542', 'https://huggingface.co/juanluisdb/MiniLM-L-6-rerank-m3', 'https://huggingface.co/cross-encoder/ms-marco-TinyBERT-L2-v2', 'https://blog.vespa.ai/pretrained-transformer-language-models-for-search-part-4/', 'https://arxiv.org/abs/2209.11755']
  - *confidence:* medium
- **Synthetic 'slip' generation with LLM relabeling, plus a small-sample-safe tuning and selection protocol**
  - *how it works:* Generate 5-20k synthetic slips that imitate the public sample. Sample source docs stratified to match the public sample's source/kind mix. Sample a window at a random depth, biased toward the middle and end of chapters to match 'buried deep'. Prompt Qwen2.5-72B-AWQ (or 32B) few-shot with about 8 real public slips: write from memory, vaguely, no titles, a paraphrase that may keep one specific detail. Produce 2-3 styles per window. Relabeling (Gecko-style): retrieve the current system's top 10 docs for each slip and have the LLM judge which doc(s) the slip describes. Drop slips with 2 or more equally valid docs, or reassign the positive. Optionally apply Promptagator round-trip filtering: keep a slip only if its doc is in the top 20 of a first-pass retriever. Use the synthetic set for training learning-to-rank, calibration and the CE, and for choosing alpha, k, window size and features. Use the public sample ONLY for validation. Selection rules: (1) compare system variants with a paired bootstrap or McNemar test on discordant questions, not raw means. Smucker et al. 2007 recommend randomization, bootstrap or t-tests over sign or Wilcoxon tests. (2) Hit@3 standard error is sqrt(p(1-p)/n): about 5.7 points at n=50 and 4.0 at n=100 when p=0.8, vs about 0.6 at n=5000 synthetic slips. Differences of 3 points or less on the public sample are noise. (3) If anything is tuned on the public sample, tune at most 2-3 parameters, with repeated 5-fold cross-validation. (4) Check that the synthetic set is a valid proxy: rank about 10 pipeline variants on synthetic and on public and require Kendall tau of about 0.6 or more. (5) Aim for public Hit@3 of 0.88 or more, to clear 0.80 on the hidden set with margin.
  - *expected effect:* Promptagator (8 or fewer examples per task): dual encoders trained on generated queries beat ColBERTv2 by more than 1.2 nDCG, and a reranker on the same data adds about 5.0 nDCG. In the Vespa-reported comparison, the few-shot dense model scored 0.478 and the few-shot CE 0.528 vs BM25 0.436 across 11 BEIR sets. Gecko: LLM relabeling changed the positive for about 15% of generated queries, and BEIR nDCG@10 went from 52.33 (seed positive) to 53.07 (LLM top-1) to 53.39 (with hard negatives). That 15% rate is very relevant to near-duplicate history chapters. Rahmani et al. (SIGIR 2024): fully synthetic test collections produced system rankings consistent with human-built ones. Bruch: CC alpha converges with under 5% of the training data. Main effect: it removes the overfitting risk of tuning on a small public sample and enables learning-to-rank and calibration at all.
  - *index size cost:* None at query time.
  - *query latency cost:* None at query time.
  - *query time dependencies:* None at query time.
  - *build recipe:* GPU: Qwen2.5-72B-AWQ needs about 40 GB of weights and 32B-AWQ about 19 GB, so neither fits in the roughly 8 GB currently free. Wait for free memory, use vLLM with cpu_offload_gb (slow), or fall back to Qwen2.5-7B-Instruct-AWQ (about 5.5 GB) for generation and use 32B or 72B only for the smaller relabeling pass later. 10k slips x about 60 output tokens is about 0.6M tokens, about 1-2 GPU-hours with vLLM on 72B-AWQ. Group cross-validation by source doc. Keep a frozen held-out synthetic test split that is never used for tuning.
  - *risks:* Style mismatch: hidden slips may be human-written, or generated with a different prompt or model. Mitigate with several prompt styles and by validating on the public sample. Round-trip filtering biases toward easy slips, which hides near-duplicate failures, so keep an unfiltered relabeled subset. Relabeling with the system under test can be circular: use the LLM judge's choice, not the retriever's. Generator leakage: slips copy rare source words more often than a human writing from memory would, which inflates lexical-signal weights. Include 'heavy paraphrase' prompts.
  - *sources:* ['https://arxiv.org/abs/2209.11755', 'https://arxiv.org/html/2403.20327v1', 'https://arxiv.org/abs/2405.07767', 'https://arxiv.org/abs/2210.11934', 'https://dl.acm.org/doi/10.1145/1321440.1321528']
  - *confidence:* high

- How many public sample questions are there, and what is their gold source/kind mix (Wikipedia vs PG books vs Country Study vs OCR Humboldt)? Synthetic slips and priors must match it.
- Were the hidden slips LLM-generated from a specific window, written by humans, or both? That decides how much weight rare-word lexical overlap deserves vs paraphrase-robust dense signals.
- Can a slip have more than one acceptable doc (for example the same event in two books), or is exactly one doc id gold? This changes how relabeling should treat ambiguous synthetic slips.
- GPU availability: only about 8 GB is free, and Qwen2.5-32B-AWQ (about 19 GB) and 72B-AWQ (about 40 GB) do not fit. When can the large model run for slip generation and relabeling, and is a 7B fallback acceptable?
- Corpus size in words and windows, which sets the BM25 postings and dense-matrix footprint (my size estimates assume 3-8M words).

### engineering

**Top recommendation:** Build the numpy-only lexical backbone first: a BM25S-style eager-scored passage index. Use overlapping ~120-content-token windows, store indptr as uint32, passage ids as uint16 and impacts as uint8 or float16, each as a separate .npy file. Score with concat + np.bincount, aggregate to docs with np.maximum.reduceat (MaxP plus a small doc-level term) and finish with argpartition. Replace the query-time stemmer with a build-time surface-form -> term-id map, keep the vocab as a newline text file or hashed uint64 array (no JSON or pickle), and call gc.freeze() after load. The measurements back this. At corpus scale (~30k passages, ~3.3M postings) it is ~10-14 MB on disk (3-4 MB with in-index zlib), loads in ~0.1-0.3 s with numpy only, and runs end to end at p50 0.24 ms / p95 0.31 ms on one core of a heavily loaded 2.2 GHz Xeon. rank_bm25 is ~130 ms per query at that scale and adds GC pauses. On real Cuba books, passage MaxP beat whole-chapter BM25 on simulated 'buried detail' queries (Hit@3 0.98 vs 0.84). So nearly the entire size, latency and load budget stays free for whatever semantic component the other researchers pick (ONNX encoder or static embeddings, doc-level float32 vectors at 0.4 ms), fused with the lexical scores. Skip static pruning beyond a query-time df cap. Every pruning variant beyond ~10% of postings cost 1-11 points of Hit@3, and the lexical index is already small. Use in-index zlib, especially on a quantized ONNX model (-25-30%), only if the size limit binds. All benchmark scripts are in /tmp/claude-1003/-mnt-data-projects-Chinese-spy-sigmoid-hack/b47426bd-f0d3-4374-bd91-a107ea984daa/scratchpad/syseng_bench/ and /tmp/claude-1003/-mnt-data-projects-Chinese-spy-sigmoid-hack/b47426bd-f0d3-4374-bd91-a107ea984daa/scratchpad/bench/ (build_synth.py, bench_query.py, bench2.py, bench_stem.py).

#### Techniques

- **Eager-scored BM25 passage index as CSR .npy arrays (BM25S-style), with concat+bincount scoring and MaxP doc aggregation**
  - *how it works:* Build time: split every doc into overlapping windows (about 120 content tokens after stopword removal, stride 60, which is about 230 raw words) and record passage->doc. Compute the full BM25 weight per (term, passage) at build time, with idf, tf saturation and length norm folded into a single number. Store a term-major CSR: indptr uint32 [V+1], indices uint16 passage ids (needs fewer than 65,536 passages, otherwise uint32), weights float16 or uint8. Keep passages contiguous per doc and store doc_start int32 [D]. Query time: ids = vocab lookups. ix = np.concatenate([indices[indptr[t]:indptr[t+1]] for t in ids]) and w the same way over the weights. s = np.bincount(ix, weights=w, minlength=P). doc = np.maximum.reduceat(s, doc_start) gives MaxP; optionally add lambda * a small doc-level BM25 vector. top = np.argpartition(-doc, 3)[:3], then sort those 3. No Python loop over postings, only over the ~5-15 query terms. A second, doc-level CSR (1,552 columns) costs about 1 MB and gives the doc-level term for free.
  - *expected effect:* Latency (my measurements: single core, thread CPU time, numpy 2.5.4 / scipy 1.18.1, Xeon Silver 4214 @ 2.2 GHz under load avg ~246 on 48 cores, so roughly 2-4x pessimistic). Synthetic Zipf index of 30k passages, 3.27M postings, 100k vocab. Typical 10-term query touching ~10k postings, median/p95: per-term loop s[idx]+=w 0.26/0.41 ms; concat+np.bincount 0.105/0.153 ms; concat+np.add.at 0.122/0.192 ms (numpy >=1.25 indexed-loop fast path, release notes say 'up to 60x faster'); scipy csr M[q].sum(0) 0.36/0.44 ms; scipy qvec@M 0.50/0.68 ms; forward-index matvec 9.3 ms. A heavy query that keeps stopword-like terms (~240k postings): bincount 1.44 ms, scipy row-slice 1.28 ms, loop 3.5 ms. End to end (regex tokenize + dict lookup + bincount + reduceat + argpartition) on 30k passages: p50 0.24 ms, p95 0.31 ms wall. On real text (7 Gutenberg Cuba books: 910k words, 183 chapters, 7,876 passages, 775k postings): median 0.086 ms, p95 0.113 ms. For comparison, rank_bm25 takes 32 ms per query on those 7,876 passages (about 130 ms at 30k), unpickles in 146 ms, and adds 93 ms gc.collect pauses, so it fails the latency limit. The BM25S paper reports up to 500x over rank_bm25 single-threaded (e.g. SciFact 953 vs 47.6 QPS, NQ 41.9 vs 0.10). Accuracy, from simulated known-item queries on the real 7-book index (3-6 tf-idf-sampled terms from one target passage plus 1-3 noise words, 600 queries): passage MaxP Hit@3 0.982 vs whole-chapter BM25 0.843 vs SumP 0.382. That supports passage-level indexing for 'buried deep inside a chapter' slips. Caveat: these queries are easier than real paraphrases. Literature: on Anserini MS MARCO doc dev, full-doc BM25 default gives RR@100 0.230 and segmented MaxP 0.268. Tuned, they are 0.278 vs 0.276, so MaxP mainly protects against badly tuned length normalization.
  - *index size cost:* About 4 bytes per posting (uint16 + float16) or 3 bytes (uint16 + uint8), plus 4 bytes per vocab entry for indptr. Real text: 775k postings = 3.2 MB for 910k words. Extrapolated to the full corpus (~3-4M words, ~30k overlapping passages, ~3-3.5M postings): ~12-14 MB at u16+f16, ~10 MB at u16+u8, plus 0.4 MB indptr for 100k terms. Without overlap it is about half that.
  - *query latency cost:* Measured 0.1-0.3 ms p95 for typical queries, up to ~1.5 ms if very common terms are not stopped. reduceat over 30k is ~0.2 ms and argpartition ~0.25 ms on this contended box. Expect well under 1 ms p95 even on an old CPU.
  - *query time dependencies:* numpy only (np.bincount, np.maximum.reduceat, np.argpartition). scipy is not needed, and it would add ~220 ms of import time.
  - *build recipe:* Python on the CPU box, a few seconds: tokenize, stem, window the text, build the CSR with scipy.sparse.csr_matrix + sum_duplicates, compute BM25 weights vectorized, cast dtypes, and np.save each array separately. Tune k1/b, window size and stride, and the MaxP vs doc-level mix on the public questions. My benchmark scripts are in /tmp/claude-1003/-mnt-data-projects-Chinese-spy-sigmoid-hack/b47426bd-f0d3-4374-bd91-a107ea984daa/scratchpad/syseng_bench/ (real_prune.py, e2e.py) and /tmp/claude-1003/-mnt-data-projects-Chinese-spy-sigmoid-hack/b47426bd-f0d3-4374-bd91-a107ea984daa/scratchpad/bench/bench_query.py.
  - *risks:* uint16 ids overflow above 65,535 passages, so check that at build time or use uint32. Overlapping windows double the postings. SumP is catastrophic on long docs (0.38), so use max or max+small doc term. bincount returns float64 (harmless). The simulated-query accuracy is optimistic. Real paraphrased slips need a semantic component on top, which is other researchers' angle.
  - *sources:* ['https://arxiv.org/abs/2407.03618 (BM25S: eager sparse scoring, single-thread QPS table)', 'https://numpy.org/doc/stable/release/1.25.0-notes.html (ufunc.at up to 60x faster)', 'https://github.com/numpy/numpy/issues/5922', 'https://github.com/castorini/anserini/blob/master/docs/regressions/regressions-msmarco-v1-doc-segmented.md', 'https://arxiv.org/abs/1905.09217 (Dai & Callan FirstP/MaxP/SumP)', 'Own micro-benchmarks (scripts in scratchpad syseng_bench/ and bench/)']
  - *confidence:* high
- **Load-time engineering: one raw .npy per array, no json/pickle/npz, vocab as text or hashed array, gc.freeze()**
  - *how it works:* Store each array as its own .npy and load it with np.load(path) or np.load(path, mmap_mode='r'). mmap applies to .npy only; .npz members are read through zipfile and cannot be memory-mapped. Avoid pickle (allow_pickle=False is the default and protects against code execution) and avoid big JSON. Vocab options: (a) a newline-joined vocab.txt, loaded with {w: i for i, w in enumerate(text.split('\n'))}; (b) a sorted fixed-width bytes array ('S' dtype) plus np.searchsorted, with an order array mapping to term ids; (c) no strings at all: a sorted uint64 array of blake2b-8-byte hashes of each term plus a uint32 id array, looked up with searchsorted. Collisions are negligible at 64 bits, and it only needs stdlib hashlib. Never use Python's hash(), which is salted per process. After loading, call gc.freeze() so the cyclic GC never rescans index objects during search(). Keep everything in numpy, not Python lists or dicts of postings. Set os.environ OMP_NUM_THREADS / OPENBLAS_NUM_THREADS / MKL_NUM_THREADS = '1' at the top of main.py before importing numpy, because the BLAS pool reads them at import. Do one warm-up search in __init__ so first-query page faults and lazy init are paid during load.
  - *expected effect:* Measured CPU ms on the contended box: np.load of 3 .npy arrays totalling 13.5 MB 12 ms (mmap 0.5 ms); npz uncompressed with all keys read 29 ms; savez_compressed npz 83 ms; json.load of a 100k-entry dict 103 ms; vocab.txt split + dict 57 ms; sorted 'S' vocab array 0.9 ms (searchsorted lookup ~12 us per query vs 2-5 us for a dict); 64-bit hash vocab 0.8 MB + 0.4 MB, e2e search p50 0.30 vs 0.24 ms with a dict. A whole lexical Retriever loads in ~0.3 s wall even with a float16->float32 cast and a text-vocab dict. Import costs (warm .pyc, wall): numpy 115 ms, scipy.sparse+numpy 330 ms, sklearn.feature_extraction.text 1.35 s, onnxruntime 175 ms, tokenizers 20-45 ms, snowballstemmer 27 ms (397 ms on first-ever import while compiling .pyc for all languages), rank_bm25 125 ms. GC: gc.collect() took 247 ms with a dict-of-lists index of 100k lists and 93 ms with rank_bm25 objects alive, and 0.00 ms after gc.freeze(). Pauses like these land directly in p95.
  - *index size cost:* None extra. The hashed vocab (1.2 MB for 100k terms) is smaller than a 'S' array, which is padded to the longest term, so OCR junk tokens inflate it.
  - *query latency cost:* Dict lookup ~2-5 us per query, hash + searchsorted ~60 us per query (blake2b in Python ~1-2 us per token plus numpy call overhead).
  - *query time dependencies:* numpy + stdlib (hashlib, re, gc, os).
  - *build recipe:* np.save each array and write the vocab once. Verify in a fresh subprocess: python -X importtime -c 'import main' and time Retriever(index_dir) cold and warm. Run the grader-like loop of N search() calls under taskset -c 0 and record p95.
  - *risks:* Whether the grader counts module import time inside 'load time' is unknown. If it does, avoid scipy and sklearn imports, since numpy alone costs ~0.1 s. mmap moves file I/O to the first query, so warm up in __init__. Thread env vars set after numpy is already imported (e.g. by the grader harness) may not take effect. In that case use numpy BLAS sparingly, since the hot path above uses no BLAS.
  - *sources:* ['https://numpy.org/doc/stable/reference/generated/numpy.load.html', 'https://docs.python.org/3/library/gc.html#gc.freeze', 'https://scikit-learn.org/stable/computing/parallelism.html (OMP/OPENBLAS/MKL env vars, threadpoolctl)', 'Own micro-benchmarks: bench/bench_query.py, bench/bench2.py, syseng_bench/rank_bm25_gc.py, syseng_bench/e2e.py']
  - *confidence:* high
- **Weight/id quantization (uint8 or float16 impacts, uint16 ids)**
  - *how it works:* Quantize BM25 impacts with a global scale: q = rint(w / (wmax/255)).astype(uint8). Scoring can sum raw uint8 values and multiply by the scale afterwards, or ignore the scale since ranking is invariant. Document ids as uint16. Lucene-style 1-byte norms and Anh/Moffat impact-ordered indexes use the same idea. Avoid float16 when a cheap uint8 works, because numpy float16 arithmetic and casts are emulated and slower.
  - *expected effect:* Simulated known-item Hit@3 on the real 7-book index: float32 0.982, float16 0.982, uint8 0.982, 4-bit (16 levels) 0.975. Crane, Trotman & O'Keefe (CIKM 2013) found that for smaller collections 8 bits is adequate for MAP and 5 bits for P@20. Speed: float16 weights cost ~20% more in the scoring loop (0.32 vs 0.26 ms typical, 4.4 vs 3.5 ms heavy); uint8 is the same speed as float32. A bulk float16->float32 cast of 11.5M elements costs ~90 ms (int8->float32 41 ms), so cast at load only if needed.
  - *index size cost:* Saves 25% vs u16+f16 (3 vs 4 bytes per posting) and 50% vs u32+f32 alternatives. About 13.5 -> 10 MB at corpus scale.
  - *query latency cost:* None, or slightly faster than float16.
  - *query time dependencies:* numpy only.
  - *build recipe:* After computing float32 BM25 weights, take a global max scale (or per-term scale stored as float32[V] if the dynamic range is large), round, then check Hit@3 on the public questions against float32 to confirm zero loss.
  - *risks:* Too few bits merges close scores and creates ties. Check tie handling in top-3. A per-term scale is needed if you mix in very differently scaled fields such as title or bigram postings.
  - *sources:* ['https://www.cs.otago.ac.nz/homepages/andrew/papers/2013-6.pdf (Crane et al., Maintaining discriminatory power in quantized indexes, CIKM 2013)', 'https://www.cs.otago.ac.nz/homepages/andrew/papers/2015-2.pdf (Lin & Trotman, anytime ranking with b-bit quantized BM25 impacts)', 'Own measurement: syseng_bench/real_prune.py']
  - *confidence:* high
- **Static index pruning: use sparingly and term-centrically, never document-centric for this task**
  - *how it works:* Options, each measured on the real 7-book passage index with 600 simulated known-item queries (baseline Hit@3 0.982, 775k postings): (1) drop terms whose doc-df=1; (2) drop the N highest-df terms (stopword-like); (3) Carmel-style term-centric top-N postings per term by impact; (4) Lassance 'T' per-term quantile; (5) Büttcher-Clarke style document/passage-centric top-k terms per passage; (6) agnostic global threshold. Keep rare terms: proper names and specific details are exactly the 'if you know, you know' signal.
  - *expected effect:* Hit@3 and postings vs unpruned (0.982, 775,315): drop doc-df=1 terms 0.968 (-1.4 pts) for only -1.8% of postings. Hapaxes are 29% of the vocab but carry 0.7% of postings, so this saves vocab strings, not postings. Drop the 100 highest-df terms: 0.972, -17% postings, and it cuts heavy-query latency from ~1.4 ms to ~0.1 ms. Term-centric top-500 per term 0.980 (-3.8%); top-200 0.975 (-10.7%); top-100 0.958 (-21%). Passage-centric top-64 terms per passage 0.942 (-35%); top-40 0.870 (-59%); top-24 0.738; top-16 0.620. Agnostic drop of the lowest 25% of weights 0.953; 50% 0.890. Literature: Lassance et al. (SIGIR 2023) found that for BM25 'all pruning strategies are too aggressive, with only a few points appearing before the effectiveness decreased too much', while learned sparse models tolerate 2x pruning at <=2% loss. Carmel et al. (SIGIR 2001) keep at least the top-k postings per term within an epsilon error bound, but the method is known to prune little in low-error settings.
  - *index size cost:* Saves 4-20% at <=1 pt cost (stoplist or top-200..500 per term). Anything beyond that costs several points. The whole unpruned index is only ~10-14 MB, so pruning is only worth it if a neural model eats the size budget.
  - *query latency cost:* Reduces p95 for queries containing very common words. A query-time IDF floor (skip terms with df > 20-30% of passages, e.g. 'cuba' is in 50% of passages and 'havana' in 27% in the real books) gets the same latency win without deleting postings.
  - *query time dependencies:* numpy only.
  - *build recipe:* Implement the variants as masks over the CSR data, eliminate_zeros, and re-evaluate on the public questions. Pick the smallest index whose Hit@3 matches unpruned. Prefer a query-time df cap to a build-time stoplist.
  - *risks:* Pruning interacts with paraphrased queries differently than with my simulated exact-term queries. Document-centric pruning removes the incidental details slips mention. Dropping df=1 terms also removes OCR-unique tokens that might be the only match for the Humboldt slice.
  - *sources:* ['https://dl.acm.org/doi/10.1145/383952.383958 (Carmel et al., Static index pruning for IR systems, SIGIR 2001)', 'https://dl.acm.org/doi/10.1145/1183614.1183644 (Büttcher & Clarke, document-centric static pruning, CIKM 2006)', 'https://arxiv.org/abs/2304.12702 (Lassance et al., A static pruning study on sparse neural retrievers, SIGIR 2023, Fig.1 and Table 1)', 'https://www.dc.fi.udc.es/~barreiro/publications/blanco_barreiro_ecir2007.pdf', 'Own measurement: syseng_bench/real_prune.py']
  - *confidence:* medium
- **In-index compression with stdlib zlib/lzma (the size limit counts bytes on disk after extraction, not the archive)**
  - *how it works:* Since index/ is measured after extraction, compressing the submission zip harder gains nothing, but compressed blobs inside index/ do count smaller. Delta-encode each posting list (ids sorted within a term; reset at indptr boundaries), optionally byte-shuffle (blosc-style byte planes), then zlib.compress(level 9) or lzma. Decode at load: zlib.decompress -> np.frombuffer -> cs = np.cumsum(delta); ids = cs - np.repeat(np.r_[0, cs][indptr[:-1]], np.diff(indptr)). For an ONNX query encoder, store model.onnx as a zlib/xz blob and pass the inflated bytes to onnxruntime.InferenceSession(bytes, sess_options).
  - *expected effect:* Real 7-book passage index: ids u16 raw -> zlib 61% / xz 41%; delta-encoded -> zlib 34% / xz 27%; float16 weights -> zlib 13% (fixed-length windows make runs of equal weights; expect less with variable-length passages); uint8 weights -> zlib 21%, xz 18% (217 distinct values, 6.6 bits entropy). Synthetic 3.27M-posting index: delta+byte-shuffle+zlib 46%, inflate 36 ms, vectorized delta decode 48 ms. Model weights: bge-small int8 ONNX 34.0 MB -> 24.4 MB zlib (72%, inflate 0.33 s) or 23.7 MB xz (70%, 1.7 s); ms-marco-MiniLM-L6 quint8 ONNX 23.2 -> 17.7 MB zlib (76%, 0.19 s); bge-small fp32 ONNX 133 -> 77.6 MB zlib / 61 MB xz; potion-base-8M float32 safetensors 30.2 -> 28.2 MB (93%, not worth it). All times are CPU on the contended box.
  - *index size cost:* Lexical index ~13 MB -> ~3-4 MB, and a quantized transformer saves ~25-30%. This can decide whether a 20-35 MB encoder fits under a tight limit.
  - *query latency cost:* Zero. All cost is at load: ~0.1 s for the lexical index, 0.2-0.35 s per 20-35 MB model with zlib. Avoid xz for big models if the load limit is ~1-2 s.
  - *query time dependencies:* stdlib zlib/lzma + numpy (+ onnxruntime for the model).
  - *build recipe:* After finalizing arrays, write <name>.zlib blobs plus a small JSON with shapes and dtypes. In __init__, inflate and np.frombuffer(...).reshape. Measure cold load in a fresh process under taskset with a single core.
  - *risks:* Rule interpretation: a grader could treat compressed blobs as fine (they are data, not code) or object if it inspects formats. Confirm against the rules text. Load time grows. Peak RAM during inflate doubles briefly. lzma decode is 5x slower than zlib.
  - *sources:* ['https://docs.python.org/3/library/zlib.html', 'https://docs.python.org/3/library/lzma.html', 'https://onnxruntime.ai/docs/api/python/api_summary.html (InferenceSession accepts a path or bytes)', 'Own measurement: syseng_bench/compress.py, syseng_bench/real_compress.py']

- **Stemmer-free query normalization: build-time surface-form -> term-id map (plus optional tiny embedded Porter for OOV)**
  - *how it works:* Do stemming only at build time. Collect every surface form in the corpus plus inflections from a large English word list (e.g. /usr/share/dict/american-english, ~100k words), stem them with Snowball or PyStemmer offline, and keep the forms whose stem exists in the index. Store surface->term_id as a newline vocab plus a uint32 id array, or as hashed uint64 keys. Add build-time synonym and spelling folds for this corpus (Havana/Habana, Guines/Güines, accent folding via NFKD, British/American 'traveller/traveler', OCR variants of the Humboldt slice mapped to their canonical term).   - *query latency cost:* ~10-30 us per query (vs ~0.6 ms with a pure-Python stemmer).
  - *query time dependencies:* stdlib only (re, unicodedata) + numpy. Removes any dependency on snowballstemmer, nltk or PyStemmer being in the grader's requirements.

  - *sources:* ['https://arxiv.org/abs/2407.03618 (BM25S Table 2: stemming/stopword ablation on BEIR)', 'https://snowballstem.org/', 'https://pypi.org/project/snowballstemmer/', 'Own measurement: bench/bench2.py, bench/bench_stem.py']

- **Optional cheap index extensions: adjacent-bigram postings and a char-trigram index restricted to the OCR slice**
  - *how it works:* Add adjacent stemmed bigrams ('vuelta_abajo', 'captain_general', 'ten_year war') as extra rows in the same CSR, keeping only bigrams that occur at least twice. With 50%-overlap windows that means df>=3. Score them like unigrams with a tuned weight lambda (a poor man's sequential dependence model). For the noisy Humboldt OCR slice only, add character-trigram postings, or better, clean the OCR at build time with the cached Qwen2.5-72B or a vocabulary-based spell corrector, so its passages match normal query terms.
  - *expected effect:* Size on the real 7-book index: bigrams with df>=3 are 55k terms and +46% of unigram postings (all bigrams would be +117%). At corpus scale that is roughly +5-6 MB at u16+f16. Character trigrams average 747 unique per ~1,400-char passage vs ~98 unigram postings, a ~7.6x blow-up, so they are only viable for a ~5% OCR slice. Retrieval gain: term-dependence (MRF/SDM, Metzler & Croft SIGIR 2005) is a well-established improvement over bag-of-words, but I could not verify specific numbers. Treat it as something to measure on the public questions.
  - *index size cost:* +40-60% postings for filtered bigrams. Char-trigrams only for the OCR slice: about +1-3 MB.
  - *query latency cost:* +0.05-0.2 ms (a few more short posting lists per query).
  - *query time dependencies:* numpy only.
  - *build recipe:* Generate bigram tokens in the same tokenizer pass, filter by df, and append rows to the CSR with their own idf. For OCR, run LLM or spell correction offline on the Humboldt chapters before indexing.
  - *risks:* Bigram weight must be tuned or it over-rewards exact phrasing that paraphrased slips will not reproduce. It needs its own vocab entries (more strings at load). Trigram scoring needs normalization so OCR passages do not dominate.
  - *sources:* ['https://ciir-publications.cs.umass.edu/pub/web/getpdf.php?id=531 (Metzler & Croft, A Markov random field model for term dependencies, SIGIR 2005)', 'Own measurement: syseng_bench/bigram.py']
  - *confidence:* low
